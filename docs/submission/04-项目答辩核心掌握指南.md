# AgentHub 项目答辩核心掌握指南

> 用途：这份文档不是替代 PRD/ADR，而是帮你在答辩前快速掌握“为什么这么做、代码怎么跑、被追问怎么答”。

## 1. 三分钟总讲稿

AgentHub 是一个 IM 式多 Agent 协作平台，可以理解成“AI 版 Slack”。用户先创建 Project，绑定一个本机或云端 workspace，然后在 Project 里创建单聊或群聊。单聊适合让一个 Agent 直接处理任务，群聊则由 Orchestrator 先理解需求、拆解任务、分派 Agent，并把执行过程和结果回流到聊天流。

项目最核心的技术点不是普通聊天，而是把 Claude Code、Codex、OpenCode 这类真实 CLI Agent 接进平台。后端通过 CLI Adapter 启动真实进程，以 Project workspace 作为 `cwd`，读取 stdout/stderr，清洗 ANSI、解析进度、文本、交互提示和产物信号，再统一转成 SSE 事件给前端。

前端采用 React + TypeScript + Vite，后端采用 FastAPI + SQLAlchemy + SQLite。桌面端用 Tauri 作为本机特权层，负责一键启动本地后端和前端，并允许访问本机文件系统和 CLI 进程；SaaS 端复用同一套 Project/Session/Agent/Artifact 领域模型，只是 workspace 和 runtime 从本机变成云端隔离环境。

系统核心闭环是：

```text
Project 绑定 workspace
  -> 用户在 Session 发消息
  -> ContextManager 组装上下文
  -> 单聊走 SingleCliChatStream，群聊走 GroupChatStream + Orchestrator
  -> CliAgentService / Adapter 启动真实 CLI Agent
  -> SSE 流式返回 token、进度、trace、approval、artifact
  -> ArtifactOutputBridge 扫描文件变化和代码块
  -> 前端 ChatWindow 展示消息级 Artifact 卡片、运行控制、审批和预览
```

答辩时可以一句话概括技术亮点：

```text
AgentHub 用 IM 交互统一人和多个 AI Agent 的协作，用 Project-first 保证文件和上下文归属，用 CLI Wrapper 接入真实 Agent 执行能力，用 Orchestrator DAG 管理复杂任务，用 Artifact 把文件变更和预览回流到消息流。
```

## 2. 架构选型怎么讲

### 2.1 为什么选 React + TypeScript + Vite

答辩回答：

```text
前端需要同时支撑 Web、桌面端和移动端壳，React 组件和状态模型可以复用；TypeScript 保证大量 SSE 事件、Artifact、Run/Task 状态的数据结构安全；Vite 启动快，适合项目快速迭代和演示。
```

代码位置：

- `frontend/src/app/AppRoot.tsx`：应用主入口和状态组装。
- `frontend/src/components/ChatWindow.tsx`：聊天主界面。
- `frontend/src/hooks/useSendMessage.ts`：发送消息和消费 SSE。
- `frontend/src/api/client.ts`：REST/SSE API 客户端。

### 2.2 为什么选 FastAPI

答辩回答：

```text
后端有大量异步流式场景，包括 SSE、WebSocket、CLI 子进程输出和云端 runtime。FastAPI 原生支持 async，接口声明清晰，和 Python 的 AI/Agent 工具生态也更容易集成。
```

代码位置：

- `backend/app/main.py`：FastAPI app、生命周期、迁移、EventBus 启动。
- `backend/app/api/chat.py`：聊天 SSE 入口。
- `backend/app/api/orchestrator.py`：编排计划执行、暂停、恢复、确认。

### 2.3 为什么选 SQLite + SQLAlchemy

答辩回答：

```text
P1 桌面版强调本机闭环和零部署，SQLite 不需要额外数据库服务，适合本机 demo 和小团队使用；SQLAlchemy 2.0 async 保留了模型层和迁移能力，后续 SaaS 化时领域模型不用推倒重来。
```

代码位置：

- `backend/app/database.py`：数据库连接和 Session。
- `backend/app/models/`：Project、Session、Message、Artifact、Run 等模型。
- `backend/migrations/`：阶段迁移脚本。

### 2.4 为什么桌面端选 Tauri

答辩回答：

```text
浏览器本身不能安全地直接访问用户本机目录或管理 CLI 进程，所以桌面端需要一个本机特权层。Tauri 可以复用前端 Web UI，同时比传统 Electron 更轻量，用来启动本地后端、打开 WebView、管理本机 Agent 进程生命周期。
```

代码位置：

- `desktop/backend_runner.py`：桌面端后端启动器。
- `desktop/src-tauri/src/main.rs`：Tauri 主入口。
- `desktop/scripts/`：构建和打包脚本。

### 2.5 为什么不是直接调 LLM API

答辩回答：

```text
课题目标不是做一个普通聊天壳，而是让 Agent 能围绕真实项目 workspace 工作。Claude Code、Codex、OpenCode 这类 CLI Agent 已经具备读写文件、运行命令、工具调用和上下文管理能力。AgentHub 通过 CLI Wrapper 把它们纳入统一产品体验，既保留真实工程执行能力，又把输出标准化为消息、进度、审批和 Artifact。
```

关键代码：

- `backend/app/services/cli_agent_service.py`：Agent Profile 到 CLI Adapter 的门面。
- `backend/app/agents/cli_adapters.py`：不同 CLI 的适配器。
- `backend/app/agents/cli_runtime.py`：CLI 进程管理。
- `backend/app/services/single_cli_chat_stream.py`：单聊 CLI 执行主链路。
- `backend/app/services/cli_agent_executor.py`：群聊中执行具体 AgentCall。

## 3. 领域模型必须讲清楚

### 3.1 Project-first

Project 是顶层组织边界：

```text
Project
  -> workspace_path / workspace_id
  -> Sessions
  -> Agent Profiles
  -> Messages
  -> Artifacts
  -> Runs / Tasks
```

为什么这么设计：

```text
如果 workspace 绑定到 Session，会导致同一个项目里的多个私聊和群聊不能自然共享文件目录。Project-first 更符合用户心智：先有项目，再围绕项目发起多个聊天；所有 Agent 都在同一个 workspace 中协作，文件变更、产物和执行记录归属清晰。
```

代码位置：

- `backend/app/services/project_service.py`：创建 Project、解析 workspace、目录安全校验。
- `backend/app/models/project.py`：Project 数据模型。
- `docs/archive/adr/0009-project-workspace-model.md`：Project-Workspace 决策。

### 3.2 Agent Profile

Agent 不是模型名，也不是 CLI 工具本身：

```text
Agent Profile =
  System Prompt
  + Rules
  + Toolset
  + Context Policy
  + Runtime Config
  + Engine
  + Avatar
```

答辩重点：

```text
Codex 不是“前端工程师”。Codex 是底层 Engine；前端工程师是一个 Agent Profile，它可以选择 Codex 作为执行引擎，也可以有自己的 System Prompt、Rules 和工具集。
```

代码位置：

- `backend/app/models/agent_config.py`：Agent 配置模型。
- `backend/app/services/cli_agent_service.py`：组装 Agent System Prompt、Rules、Toolset。
- `docs/archive/adr/0011-agent-engine-skill-model.md`：Agent Profile 决策。

### 3.3 Session

Session 是聊天会话，分为：

- 单聊：一个 Session 关联一个 Agent。
- 群聊：一个 Session 包含多个 Agent，由 Orchestrator 做分流、计划或协作。

代码位置：

- `backend/app/services/session_service.py`
- `backend/app/api/sessions.py`
- `frontend/src/stores/sessionStore.ts`

### 3.4 Message

Message 不只是文本，还承载来源、引用、Pin、运行状态、Artifact 关联、Orchestrator 执行快照等 metadata。

常见追问回答：

```text
引用和 Pin 不是前端显示效果，而是会进入 ContextManager 的 prompt 组装。这样 Agent 真正能看到用户引用或固定的上下文。
```

代码位置：

- `backend/app/services/message_service_sqlalchemy.py`
- `backend/app/domain/context_manager.py`

### 3.5 Artifact

Artifact 是 Agent 产物标准回流形态，包括：

- `code_diff`
- `web_preview`
- `document`
- `file_tree`

答辩重点：

```text
Artifact 不是前端临时从 Markdown 扫出来的装饰，而是后端根据 CLI 输出、代码块、workspace diff 和执行 trace 创建的持久化产物，绑定具体 message、project、version 和 file_path。
```

代码位置：

- `backend/app/services/artifact_output_bridge.py`：CLI 输出完成后的产物扫描。
- `backend/app/services/artifact_service.py`：Artifact 创建、版本、编辑。
- `frontend/src/components/ArtifactCard.tsx`
- `frontend/src/components/MessageArtifactStrip.tsx`

## 4. 核心链路一：单聊真实 CLI Agent

单聊流程：

```text
1. 用户在 ChatInput 输入消息
2. useSendMessage 做环境体检 checkSystemHealth
3. createChatStream POST /sessions/{session_id}/chat
4. ChatServiceImpl 持久化用户消息，创建 Run/Task
5. ContextPackService + ContextManager 组装历史、引用、Pin
6. SingleCliChatStream 找到 session 绑定的 Agent
7. SessionService 找到 Project workspace_path
8. EngineSessionService 判断是否复用 CLI 原生会话
9. CliAgentService 组装 prompt，调用对应 CLI Adapter
10. Adapter 启动真实 CLI 进程并解析输出
11. 后端持续 yield SSE：token、process、trace、interactive_prompt
12. CLI 结束后保存 assistant message
13. ArtifactOutputBridge 扫描 workspace diff 和代码块
14. 前端更新消息、运行状态、Artifact 卡片
```

最应该熟悉的代码：

- `frontend/src/hooks/useSendMessage.ts`
- `frontend/src/api/client.ts` 的 `createChatStream`
- `backend/app/api/chat.py` 的 `chat`
- `backend/app/services/chat_service_impl.py` 的 `send_message_stream`
- `backend/app/services/single_cli_chat_stream.py` 的 `send`
- `backend/app/services/cli_agent_service.py` 的 `stream`
- `backend/app/agents/cli_adapters.py` 的 `CliAgentAdapter.stream`

答辩金句：

```text
单聊链路的关键是把用户消息变成 Project workspace 中的一次真实 CLI Agent turn，并把 CLI 的非结构化输出标准化成前端可消费的事件流。
```

## 5. 核心链路二：群聊 Orchestrator 协作

群聊不是简单“多个 Agent 同时回答”，而是有调度逻辑。

主要流程：

```text
1. 用户在群聊发消息
2. ChatServiceImpl 判断 session.mode == group
3. GroupChatStream 获取群成员和 workspace
4. 如果 @ Orchestrator，进入 plan-first 计划生成
5. 如果没有 @，OrchestratorStewardChat 先判断路由：
   - context_only：只记录上下文
   - direct_dialog：切到某个 Agent 直接对齐
   - draft_plan / mini_collab：生成计划
   - single_agent：分派给具体 Agent
6. OrchestratorV2 执行 Pipeline：
   - IntentAnalyzer 分析意图
   - ContextManager 组装上下文
   - AgentSelector 选择 Agent
   - ExecutionPlanner 生成 single / chain / dag 执行模式
7. AgentExecutor 按模式执行 AgentCall
8. GroupChatFinalizer 持久化每个 Agent 消息并生成中枢总结
9. 前端 CollaborationPanel 展示任务、DAG phase、运行状态
```

核心代码：

- `backend/app/services/group_chat_stream.py`
- `backend/app/domain/orchestrator_v2.py`
- `backend/app/domain/intent_analyzer.py`
- `backend/app/domain/agent_selector.py`
- `backend/app/domain/execution_planner.py`
- `backend/app/services/agent_executor.py`
- `backend/app/services/group_chat_finalizer.py`
- `frontend/src/components/CollaborationPanel.tsx`

Orchestrator Pipeline 可以这样讲：

```text
OrchestratorV2 是 Domain 层的 thin coordinator，不直接依赖 FastAPI 或数据库。它只负责把一次群聊请求经过意图分析、上下文组装、Agent 选择和执行计划生成，输出 PipelineResult。真正的 I/O 执行放在 Service 层的 AgentExecutor。
```

## 6. 核心链路三：Artifact 如何产生

Artifact 产生有两类来源：

1. CLI 消息里明确输出的代码块，例如 HTML、Diff、Markdown。
2. Agent 执行前后 workspace 的文件变化。

流程：

```text
1. CLI 执行前 FileChangeDetector 创建 workspace snapshot
2. CLI 执行后 SingleCliChatStream / GroupChatFinalizer 保存 assistant message
3. ArtifactOutputBridge.scan_completed_message 开始扫描
4. 对比 snapshot 得到创建/修改文件
5. 对 HTML、Markdown、图片、PDF、Office、Diff 等类型生成候选 Artifact
6. 结合 execution trace 提升置信度
7. 高置信度候选写入 Artifact 表
8. 通过 SSE 发 artifact.created
9. 前端 MessageArtifactStrip 在对应消息下展示 ArtifactCard
```

核心代码：

- `backend/app/services/file_change_detector.py`
- `backend/app/services/artifact_output_bridge.py`
- `backend/app/services/artifact_preview.py`
- `backend/app/services/artifact_service.py`
- `frontend/src/components/MessageArtifactStrip.tsx`
- `frontend/src/components/ArtifactReviewModal.tsx`

答辩金句：

```text
Artifact Bridge 解决的是“Agent 改了文件但用户不知道改了什么”的问题。它把文件系统变化转成消息级、可预览、可版本化、可追溯的产品对象。
```

## 7. 核心链路四：前端如何消费流式事件

前端事件消费集中在 `useSendMessage` 和 `createChatStream`。

关键事件类型：

| 事件 | 前端用途 |
| --- | --- |
| `run.started` | 创建运行态，显示运行控制条 |
| `task.status_changed` | 更新任务状态 |
| `agent.process.started` | 显示 CLI 进程启动和 trace |
| `agent.output` | 流式追加消息 token |
| `interactive_prompt` | 显示用户确认卡片 |
| `agent.trace.delta` | 展示工具调用、进度、错误等执行轨迹 |
| `artifact.scan.started` | 显示产物扫描中 |
| `artifact.created` | 在消息下挂 Artifact 卡片 |
| `approval.created` | 显示审批节点 |
| `orchestrator.task_started` | 展示协作任务面板 |
| `orchestrator.phase_change` | 更新 DAG phase 状态 |

答辩回答：

```text
前端不是等完整响应返回后一次性渲染，而是通过 SSE 增量消费后端事件，把聊天文本、Agent 进程状态、任务状态、审批和 Artifact 分别写入 Zustand store。这样用户能实时看到 Agent 正在做什么。
```

核心代码：

- `frontend/src/api/client.ts` 的 `createChatStream`
- `frontend/src/hooks/useSendMessage.ts`
- `frontend/src/stores/chatStore.ts`
- `frontend/src/components/ChatWindow.tsx`

## 8. 核心链路五：Local 与 SaaS 如何共用模型

本机版和 SaaS 版的差别不是产品模型，而是 runtime provider。

```text
P1 Local Desktop:
  workspace = 本机目录
  runtime = 用户电脑上的 CLI 进程
  数据 = 本机 SQLite

P2 SaaS Cloud:
  workspace = 云端隔离 workspace
  runtime = 云端 sandbox / runner
  数据 = 云端服务和多租户资源
```

在聊天入口中的分支：

```text
backend/app/api/chat.py
  if project.workspace_mode == "cloud":
      CloudAgentRuntimeService.stream_chat / stream_group_chat
  else:
      ChatServiceImpl.send_message_stream
```

答辩回答：

```text
我们把 Project、Session、Agent、Message、Artifact、Run 这些领域对象保持一致，本机和云端只替换 workspace provider、runtime provider、权限和存储实现。这样桌面端先跑通真实闭环，SaaS 能在同一模型上扩展团队、RBAC、快照、部署。
```

核心代码：

- `backend/app/api/chat.py`
- `backend/app/services/cloud_agent_runtime.py`
- `backend/app/services/cloud_workspace_provider.py`
- `backend/app/services/sandbox_service.py`
- `backend/app/services/deployment_provider.py`

## 10. 常见追问与回答

### Q1：你们的多 Agent 协作和普通群聊有什么区别？

回答：

```text
普通群聊只是多个对象在同一个界面发消息。AgentHub 的群聊有 Orchestrator：它会分析意图、选择 Agent、生成执行计划，并按 chain 或 DAG 模式执行。每个 Agent 的输出会进入共享上下文，后续 Agent 可以基于前序结果继续工作，最后还有中枢总结。
```

### Q2：为什么要有 Project，不直接创建聊天？

回答：

```text
因为 Agent 的核心能力是读写项目文件。Project 绑定 workspace 后，Project 下所有私聊和群聊共享同一目录，消息、文件变化、Artifact 和执行记录都有统一归属。如果直接创建聊天，workspace 归属会混乱，也不利于多个 Session 围绕同一项目协作。
```

### Q3：CLI Adapter 最难的地方是什么？

回答：

```text
难点在于不同 CLI 的输出格式、进度表示、交互确认、会话恢复机制都不一样。Adapter 需要把 stdout/stderr、JSONL、ANSI 控制符、交互提示、错误和文件变化统一转成 AgentHub 标准事件，例如 agent.output、interactive_prompt、artifact.created。
```

### Q4：如何保证 Agent 看到正确上下文？

回答：

```text
ContextManager 会按 token 预算组装 prompt，System Prompt 固定在前，Pin 消息优先保留，当前引用和当前轮消息优先保留，普通历史按最近优先填充。如果超预算，会截断低优先级内容，保证用户当前意图和显式固定内容不丢失。
```

### Q5：如何知道 Agent 改了哪些文件？

回答：

```text
CLI 执行前会创建 workspace snapshot，执行后用 FileChangeDetector 做 diff。ArtifactOutputBridge 根据变更文件、代码块和执行 trace 生成 Artifact 候选，高置信度的候选会持久化为消息级 Artifact，并在前端显示预览、Diff、版本和编辑入口。
```

### Q6：如何处理长任务和用户中断？

回答：

```text
后端用 Run/Task/Process 记录运行状态，SSE 持续推送状态变更。前端 RuntimeControlStrip 可以取消运行；后端会通过 run_service 和 cli_runtime_registry 绑定 processId，并在取消时中止对应进程或把 Orchestrator execution 标记为 interrupted。
```

### Q7：为什么有 EventBus？

回答：

```text
EventBus 用来解耦生命周期事件，比如项目创建、Orchestrator 任务开始、Artifact 检测、workspace 文件变化。这样 API、服务层、WebSocket 推送和审计不需要互相硬编码调用。
```

### Q8：项目如何支持多端？

回答：

```text
Web UI 是核心体验；Local Desktop 用 Tauri 包住同一套前端，并启动本地后端和 CLI runtime；Mobile 用 Capacitor 做轻量查看、审批和预览。三端通过 capabilities 区分能力，不复制三套业务逻辑。
```

### Q9：SaaS 云端如何保证隔离？

回答：

```text
云端 Project 使用 cloud workspace id，不把物理路径暴露给前端；请求经过 AuthService、TenantGuard 和 RBAC 校验；Agent runtime 在云端 sandbox/runner 中执行，Secret、Quota、AuditLog 和 deployment provider 独立建模。
```

### Q10：项目最大的技术亮点是什么？

回答：

```text
我认为最大亮点是把真实 CLI Agent 的工程执行能力产品化：用户用 IM 方式发起任务，后端把任务路由到真实 workspace 中的 CLI Agent，输出再被标准化为消息、执行轨迹、审批和 Artifact。这比简单聊天更接近真实软件协作。
```

## 11. 演示路线建议

### 11.1 本机桌面端主线

1. 启动 AgentHub Local Desktop。
2. 创建 Project，绑定一个本机 workspace。
3. 创建一个单聊，选择 Codex 或 Claude Code Agent。
4. 让 Agent 修改或生成一个文件。
5. 展示消息流中的 token、进度、执行 trace。
6. 展示 Artifact 卡片、预览、Diff 或版本。

## 12. 复习优先级

### 第一优先级：必须能讲

- AgentHub 的一句话定位。
- Project-first 为什么必要。
- Agent Profile 和 Engine 的区别。
- CLI Wrapper 为什么比直接 API 聊天更适合本项目。
- 单聊请求从前端到 CLI 再到 Artifact 的完整链路。
- 群聊 Orchestrator 的 Pipeline 和 DAG。

### 第二优先级：最好能讲

- SSE 事件如何驱动前端实时 UI。
- ContextManager 如何处理 Pin、Reply 和 token budget。
- ArtifactOutputBridge 如何根据 workspace diff 产生 Artifact。
- Local Desktop 和 SaaS Cloud 如何共用模型。
- Run/Task/Approval 如何支撑运行控制和人机确认。

### 第三优先级：被问到再展开

- Engine session resume 和 persistent process。
- Cloud sandbox、quota、secret、deployment provider。
- FTS 搜索、消息转发、移动端审批。
- 测试策略和阶段归档。

## 13. 一句话背诵版

```text
AgentHub 是一个 Project-first 的多 Agent 协作平台。前端用 IM 方式承载用户和 Agent 的交互，后端用 FastAPI 管理 Session、Message、Run、Artifact 和 Orchestrator；真正的 Agent 执行不是简单调用模型 API，而是通过 CLI Adapter 启动 Claude Code、Codex、OpenCode 等真实 CLI 工具，让它们在 Project workspace 里读写文件。执行输出被标准化为 SSE 事件，前端实时展示消息、任务状态、执行轨迹、审批和 Artifact。复杂任务由 Orchestrator 分析意图、选择 Agent、生成 chain/DAG 计划并调度执行，本机桌面端和 SaaS 云端复用同一领域模型，只替换 workspace 与 runtime provider。
```
