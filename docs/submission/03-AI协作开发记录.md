# AgentHub AI 协作开发记录

## 1. 概述

AgentHub 的课题考察重点中，AI 协作能力占比最高。项目不只是“使用 AI 写代码”，而是把 AI 协作过程沉淀成可复用、可审计、可持续演进的工程体系。

项目采用三层 AI 协作体系：

```text
Rules：长期规则，规定 AI 如何工作
  ↓
Spec：阶段规格，规定每个功能要做什么、怎么验收
  ↓
Skill：可复用工作流，规定遇到某类任务时如何执行
```

再配合 Dev Log、ADR、测试协议和阶段交付快照，形成完整的人机协作闭环。

## 2. Rules：长期协作规则

Rules 是每次 AI 协作都必须遵循的长期约束。项目中主要体现在：

| 文件 | 作用 |
| --- | --- |
| `AGENTS.md` | Codex / AI Agent 行为规则、技术栈、架构约束、代码规则、文档规则、Git 规则。 |
| `CLAUDE.md` | Claude Code 使用的项目规则镜像，确保不同 Agent 遵循同一套约束。 |
| `CONTEXT.md` | 项目全局上下文，统一领域术语、架构、Phase 状态和文档索引。 |

Rules 解决的问题：

1. 防止 AI 每次从零理解项目。
2. 避免不同 Agent 使用不同架构风格。
3. 明确禁止事项，例如不能绕过真实 CLI Agent、不能未经人工验收提交 Git。
4. 统一文档语言、代码注释、测试和真实服务验收要求。

## 3. Spec：阶段规格与验收标准

Spec 是项目与 AI 协作的主要契约。每个 Phase 都有明确的范围、验收标准和非目标，避免 AI 在实现时发散。

仓库位置：

```text
docs/specs/
```

典型规格：

| Spec | 内容 |
| --- | --- |
| `docs/specs/phase3/` | Orchestrator、DAG、协作面板。 |
| `docs/specs/phase6/` | Workspace Runtime、CLI Adapter、Artifact Bridge、Agent Profile。 |
| `docs/specs/phase7/` | 运行控制、审批、环境体检、IM 体验、演示闭环。 |
| `docs/specs/phase9/` | Cloud Workspace Foundation。 |
| `docs/specs/phase10/` | Sandbox Runner 与云端 Agent Runtime。 |
| `docs/specs/phase13/` | Local Desktop、SaaS Web、Mobile 三端产品壳。 |

Spec 带来的收益：

1. AI 执行任务前有明确上下文。
2. 用户可以按验收标准人工测试。
3. 复杂 Phase 可以拆成多个可交付切片。
4. 后续调试时能追溯“为什么这样做”。

## 4. Skill：可复用 AI 工作流

Skill 把重复出现的 AI 协作模式固化为可调用流程。

仓库位置：

```text
.agents/skills/
```

当前核心 Skill：

| Skill | 用途 |
| --- | --- |
| `agenthub-module-dev` | 新模块开发：读取 Spec、确认契约、实现、测试、验收。 |
| `agenthub-code-review` | 代码审查：接口契约、UX 状态、测试覆盖、Git 规范。 |
| `agenthub-phase-wrapup` | 阶段收尾：文档审计、开发日志、下阶段文档、资产沉淀。 |
| `agenthub-qa-audit` | 质量审计：真实服务、浏览器自动化、端到端链路、UX 状态检查。 |

Skill 的价值：

1. 把高频协作方式从“临时提示词”变成“项目资产”。
2. 降低不同 AI Agent 接手任务的沟通成本。
3. 让开发、审查、测试、收尾流程更稳定。
4. 形成可复用、可追溯的 AI 协作方法论。

| `phase3-dev-log.md` | Orchestrator 设计、群聊协作、测试覆盖演进。 |

4. 让后续 Agent 能接续上下文。

## 7. 典型 AI 协作案例

### 7.1 Orchestrator 群聊调度

早期群聊容易变成简单 @Agent 回复，后来通过 PRD、ADR、Spec 逐步收敛为 Orchestrator 计划生成、DAG 调度、任务执行和用户审批的完整流程。

沉淀材料：

- `docs/adr/0007-orchestrator-architecture.md`
- `docs/specs/phase3/02-orchestrator/`
- `docs/specs/phase7/08-orchestrator-execution-resume.md`

### 7.2 真实 CLI Agent 接入

项目明确拒绝“HTTP LLM API 伪 Agent”方案，改用真实 CLI 进程封装。AI 协作过程中围绕进程管理、stdout/stderr、ANSI 清洗、交互提示、workspace diff 和常驻 session 逐步迭代。

沉淀材料：

- `docs/PRD/01-Architecture_Adapter.md`
- `docs/specs/phase6/01-cli-adapter.md`
- `docs/deliverables/phase6-cli-adapter/`

### 7.3 Artifact 产物回流

为了让 Agent 产物不是散落在文件系统中，项目设计了消息级 Artifact。AI 协作中逐步完成 Artifact 卡片、文件编辑器、代码引用、版本链和 Diff。

沉淀材料：

- `docs/adr/0010-message-level-artifact-experience.md`
- `docs/specs/phase6/02-artifact-output-bridge.md`
- `docs/deliverables/phase6-artifact-bridge/`

### 7.4 桌面端打包与本地后端生命周期

桌面端需要做到双击启动、本地后端自动拉起、关闭窗口释放进程。AI 协作过程中通过构建脚本、Tauri 配置、后端 sidecar 和进程生命周期管理完成收口。

沉淀材料：

- `desktop/`
- `docs/specs/phase13/README.md`
- `docs/deliverables/phase13-product-shells/`

### 7.5 SaaS 云端能力扩展

## 8. 人工验收与测试闭环

AI 协作过程中，项目强调“AI 写完不等于完成”，必须经过测试和人工验收。

验收方式包括：

1. 后端 pytest。
2. 前端 vitest 和 TypeScript 检查。
3. Playwright 浏览器自动化。
4. 真实服务启动验收。
5. 桌面端打包和手动体验。
6. 用户人工验收后再允许 Git 提交。

相关材料：

- `docs/TEST_PROTOCOL.md`
- `docs/testing/UX_TEST_SPEC.md`
- `docs/deliverables/*/acceptance-log.md`
- `AGENTS.md`

| 维度 | 收益 |
| --- | --- |
| 开发速度 | 多个阶段可以通过 Spec 驱动快速推进。 |
| 质量控制 | Rules 和测试协议减少临时实现和架构漂移。 |
| 可追溯性 | ADR、Dev Log、deliverables 记录每次重要变化。 |

| 答辩展示 | AI 协作过程本身成为高权重交付物。 |

## 10. 反思与改进

项目也暴露了 AI 协作中的挑战：

1. 上下文很长时需要更强的阶段索引和交接机制。
2. 群聊调度中的人机控制权需要明确状态机支持。
3. AI 容易过度拆分任务，需要通过 Spec 限制粒度。
4. 长任务需要可靠的中止、恢复和交接文档。
5. 文档必须持续治理，否则容易出现重复和过期。

这些问题已经反向推动了项目中的 Orchestrator resume、direct dialog、运行控制、README/CONTEXT 索引和 Skill 流程沉淀。
