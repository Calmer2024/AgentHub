**版本**: v1.0
**创建日期**: 2026-05-26
**适用范围**: AgentHub 所有开发阶段
**关联文档**: [TEST_PROTOCOL.md](../TEST_PROTOCOL.md)

---

## 1. 原则

### 1.1 核心信念

> **功能正确是底线，体验正确是标准。** 一个功能即使逻辑无误，如果用户感知不到反馈、产生困惑、或误判系统状态——那就是 bug，不是"优化"。

### 1.2 体验测试三定律

| 定律 | 含义 |
|------|------|
| **反馈定律** | 系统对用户的每一次操作，必须在 200ms 内给出**可见**的反馈（即使是"我在处理"） |
| **状态定律** | 界面必须让用户在任何时刻清楚回答三个问题：系统在做什么？我能做什么？接下来会发生什么？ |
| **恢复定律** | 任何错误发生后，用户必须有明确的恢复路径（重试、返回、或清晰的状态说明） |

### 1.3 UX 测试的地位

- UX 测试与功能测试**同等权重**。Phase 验收时，功能测试 + UX 测试必须**全部通过**。
- 功能测试回答"对不对"，UX 测试回答"用户会不会困惑"。
- 两者互不替代。

## 2. 状态覆盖模型

每个可见组件必须覆盖以下 **6 种状态**。遗漏任一状态即为测试不完整。

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│ 空状态    │    │ 加载中   │    │ 正常态   │
│ (Empty)   │    │ (Loading) │    │ (Normal)  │
└──────────┘    └──────────┘    └──────────┘

┌──────────┐    ┌──────────┐    ┌──────────┐
│ 错误态   │    │ 边界态   │    │ 完成态   │
│ (Error)   │    │ (Edge)    │    │ (Done)    │
└──────────┘    └──────────┘    └──────────┘
```

### 2.1 各状态定义

| 状态 | 场景 | 用户期望 |
|------|------|---------|
| **空状态** | 首次使用、列表为空、无历史数据 | 提示如何开始（引导文案 + 行动按钮），不是空白页 |
| **加载中** | 数据请求中、AI 思考中、文件上传中 | 明确的加载指示器（骨架屏/脉冲动画/打字指示器），不是空白或假死 |
| **正常态** | 常规使用、数据已展示 | 内容清晰可读，交互可操作 |
| **完成态** | 流式结束、上传完成、操作成功 | 短暂的成功反馈（可选），状态迁移到正常态 |
| **错误态** | API 失败、网络断开、超时 | 红色/橙色文字说明原因 + 可操作按钮（重试/返回），不要让用户猜 |
| **边界态** | 极长文本、极快/极慢响应、并发操作、快速切换 | 不崩溃、不丢失数据、不产生错误的状态叠加 |

## 3. 组件级 UX 检查清单

### 3.1 通用检查项（每个组件）

```
□ 空状态   - 是否有引导内容？用户知道下一步做什么吗？
□ 加载中   - 是否有加载指示器？视觉上是否和静态内容有区别？（动画/脉冲/骨架）
□ 正常态   - 内容是否按时出现？布局是否稳定（不跳动）？
□ 完成态   - 是否有完成信号？（如流式结束 → 移除加载指示器）
□ 错误态   - 错误信息是否用用户能理解的语言？是否有操作入口（重试等）？
□ 边界态   - 极长文本是否截断/换行？极快响应是否闪屏？极慢响应是否超时？
```

### 3.2 Chat 场景专用检查项

#### 3.2.1 消息发送流程

| # | 检查项 | 通过标准 |
|---|--------|---------|
| C1 | 发送按钮点击后 | 用户消息立即出现在对话区（乐观更新），不是等后端返回 |
| C2 | AI 响应等待中 | AI 气泡区域显示**打字指示器**（跳动的三个点或波浪线），不是空白气泡 |
| C3 | 输入框 | 流式中禁用，placeholder 变为"AI 正在回复..."或等价提示 |
| C4 | 发送按钮 | 流式中禁用 + 视觉降级（opacity/gray），防止重复发送 |
| C5 | 首 token 到达 | 打字指示器立即消失，内容开始渲染 |
| C6 | 流式执行中 | 滚动条自动跟随最新内容，用户不需手动滚 |
| C7 | 流式完成 | AI 气泡恢复静态样式，输入框恢复可用，发送按钮恢复可用 |
| C8 | 流式超时 (60s 无 token) | 显示"AI 响应超时"，保留已接收内容，允许重试 |
| C9 | 多轮对话 | 每次发送新消息时，旧消息的 AI 气泡保持完整，不影响状态 |

#### 3.2.2 会话列表

| # | 检查项 | 通过标准 |
|---|--------|---------|
| S1 | 空列表 | 显示引导文案："点击下方「新建对话」开始"或等价，不是纯白区域 |
| S2 | 新建会话 | 列表顶部立即出现新会话（乐观更新），自动选中 |
| S3 | 切换会话 | 消息区立即更新，不出现上一个会话的残留内容 |
| S4 | 删除会话（未来功能）| 确认弹窗 → 列表更新 → 如果删的是当前会话，自动切换到下一个 |

#### 3.2.3 消息气泡

| # | 检查项 | 通过标准 |
|---|--------|---------|
| B1 | 用户消息 | 右对齐、蓝色背景、正确显示时间 |
| B2 | AI 消息（流式中） | 左对齐、灰色背景、打字指示器/光标闪烁 |
| B3 | AI 消息（完成） | 左对齐、灰色背景、显示完整文本 |
| B4 | 极长消息 (>1000 字) | 正确换行，不溢出容器，不撑破布局 |
| B5 | 包含代码/符号的消息 | 等宽字体渲染，特殊字符不显示为乱码 |
| B6 | 错误消息 | 红色文字、错误图标、可重试 |

#### 3.2.4 网络与连接

| # | 检查项 | 通过标准 |
|---|--------|---------|
| N1 | SSE 连接断开 | 显示"连接中断" + 已接收内容保留 + 重试按钮 |
| N2 | HTTP 错误 (4xx/5xx) | 显示具体错误信息（不是"出错了"），颜色区分错误级别 |
| N3 | 离线状态 | 检测并提示，禁用来发送 |
| N4 | 服务器未启动 | 页面加载时就检测，显示"无法连接到服务器"，不是白屏 |

## 4. 时间体验指标

| 指标 | 阈值 | 测量方法 |
|------|------|---------|
| 点击发送 → 用户消息可见 | < 100ms | Performance API / 肉眼 |
| 点击发送 → 打字指示器出现 | < 200ms | Performance API |
| 点击发送 → 首 token 到达 | < 3s (Spec 要求) | SSE 首事件时间戳 |
| 打字指示器 → 首 token 到达 | 任意（指示器就是为这个等待设计的） | — |
| 页面首次加载 → 可交互 | < 2s | Lighthouse / Playwright |
| 流式完成 → 输入框恢复 | 即时（同一帧） | 观察 |

## 5. 测试方法

### 5.1 自动化（Playwright）

```typescript
test("shows typing indicator while waiting for AI response", async ({ page }) => {
  await page.goto("/");
  await page.click("text=新建对话");
  await page.fill('[role="textbox"]', "Hello");
  await page.click("text=发送");

  // 用户消息立即出现
  await expect(page.locator(".message.user")).toBeVisible();

  // 打字指示器出现
  await expect(page.locator(".typing-indicator")).toBeVisible({ timeout: 500 });

  // 发送按钮禁用
  await expect(page.locator("text=发送")).toBeDisabled();
});
```

### 5.2 手动（结构化检查）

每次 Phase 验收时，按本规范第 3 节的检查清单逐条打勾。

手动检查规则：
- 使用 Chrome DevTools Network throttling（Slow 3G）模拟慢网络
- 使用 React DevTools 检查不必要的重渲染
- 每个检查项在 Chrome + Firefox 两个浏览器通过

### 5.3 幻觉测试（Hallucination Test）

让不了解项目的同事使用，录制屏幕 + 出声思考。观察：
- 有没有愣住不确定该点哪里的时刻？
- 有没有"它在干嘛？"的疑问？
- 有没有等得不耐烦的时刻？

## 6. UX Bug 分级

| 级别 | 定义 | 示例 |
|------|------|------|
| **P0 阻断** | 用户会认为系统坏了/卡死了，不知道怎么办 | 发送后无任何反馈，白屏，无限 loading |
| **P1 严重** | 用户能完成操作但体验明显受损 | 空白气泡代替打字指示器，错误信息用英文/技术术语 |
| **P2 一般** | 不符合直觉但用户能绕过 | 滚动条不跟随，切换会话后布局跳动 |
| **P3 优化** | 锦上添花 | 过渡动画时长、颜色微调 |

P0 和 P1 **必须**在当前 Phase 修复后才能标记完成。

## 7. 与功能测试的集成

在 [TEST_PROTOCOL.md](../TEST_PROTOCOL.md) 的阶段验收流程中，UX 测试作为一个独立环节：

```
Phase 完成前:
  1. 冒烟测试 × 2 (backend + frontend)        ← 功能
  2. 全量 API 测试                              ← 功能
  3. 全量前端组件测试                            ← 功能
  4. UX 状态覆盖检查（本规范第 3 节）              ← 体验  ← NEW
  5. E2E 测试 (核心路径)                         ← 混合
  6. 手动验证清单 (Spec 第 4 节)                  ← 混合
  7. 全部通过 → Phase 标记为 Completed
```

## 8. Phase 1 当前 UX 缺陷（示例）

本阶段已识别的 UX 问题，作为本规范的第一批实践对象：

| ID | 组件 | 状态 | 问题描述 | 级别 |
|----|------|------|---------|------|
| UX-1 | MessageBubble | 加载中 | AI 等待响应时，气泡 content 为空 → 显示为一个灰色空白框，用户以为界面卡死 | **P0** |
| UX-2 | ChatInput | 加载中 | placeholder 始终显示"输入消息..."，不反馈"AI 正在回复" | **P1** |
| UX-3 | SessionList | 空状态 | 首次使用时左侧是空列表，没有任何引导文案 | **P1** |
| UX-4 | ChatWindow | 加载中 | 没有全局的 AI 思考指示器（如顶部横幅"AI 正在回复..."） | **P2** |
| UX-5 | ChatWindow | 错误态 | `onDone` 收到 error 时仅 `setIsStreaming(false)`，不向用户展示错误 | **P1** |
