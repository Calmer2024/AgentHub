# 动态 Agent 协作模型重构方案

> 以固定项目Leader为唯一调度者，以普通 Agent为具备独立上下文的可调用成员，以公开群聊消息作为协作界面，以版本化计划和持久化事件作为事实记录，以 Git worktree作为并行写入隔离，由项目Leader在每个关键事件后动态决定下一步。

## 1. 文档定位

本文独立定义 AgentHub 下一代群聊协作模型的目标架构、交互规则、状态模型、权限边界、上下文机制、Git 隔离方案、数据模型和迁移路径。

本方案是一套从目标模型出发设计的根本性重构，不依赖其他方案文档作为前提。

## 2. 重构目标

新模型需要实现以下目标。

1. 项目Leader真正掌握协作决策权，而不是充当固定工作流中的计划生成节点。
2. 普通 Agent 作为项目Leader可选择调用的成员工具，但保留独立上下文和自主执行能力。
3. 用户、项目Leader和普通 Agent 的所有正式协作都发生在可见群聊中。
4. 计划可以在执行中版本化演进，不冻结为不可修改的静态 DAG。
5. 后端负责权限、持久化、状态校验、事件投递、隔离和恢复，不替项目Leader作语义决策。
6. 不同 Agent 可以并行工作，同一 Agent 在同一群聊中保持串行。
7. 所有写入任务通过 Git worktree 隔离，验收后再合并。
8. 应用重启、进程中断和计划变更后，协作事实仍可恢复和审计。

核心原则如下。

> 后端维护秩序和事实，项目Leader决定行动，普通 Agent执行并汇报，用户拥有最终意图和高风险操作的决定权。

## 3. 角色与权限

### 3.1 用户

用户拥有以下权限。

- 向群聊发送需求、补充信息和控制指令。
- 直接 `@` 任意普通 Agent。
- `@` 项目 Leader 触发任务协作。
- 一次不能 `@` 多个普通 Agent。
- 在批准模式中批准、要求修改或取消计划。
- 暂停、继续、停止或修改协作任务。
- 对系统规定的高风险操作进行最终确认。

### 3.2 项目Leader

第一阶段每个群聊自动包含一个固定、唯一、系统内置的项目Leader。

项目Leader拥有以下独占权限。

- 对齐用户需求。
- 判断需求是否足以生成计划。
- 生成和修改计划。
- 调用普通 Agent。
- 创建任务、返工、改派和独立验收任务。
- 验收 Agent 汇报。
- 判断哪些后续任务可以启动。
- 处理 Agent 的协助请求。
- 向用户提出问题或风险确认。
- 发布最终总结并结束协作任务。

### 3.3 普通 Agent

普通 Agent拥有以下能力。

- 接收用户直接消息。
- 接收项目Leader的正式委派。
- 读取当前群聊的完整历史。
- 读取工作区。
- 在被分配的 worktree 中执行写入任务。
- 向项目Leader提交完成、失败、阻塞、风险和协助请求。

普通 Agent明确不具备以下能力。

- 调用或唤醒其他普通 Agent。
- 创建下级 Agent。
- 修改协作计划。
- 直接结束整个协作任务。
- 绕过项目Leader请求用户批准。

### 3.4 后端协调基础设施

后端不承担语义调度，只提供以下确定性能力。

- 权限检查。
- 事件队列和唤醒。
- 状态持久化。
- 任务依赖可用性计算。
- 同一 Agent 串行锁。
- Git worktree 生命周期管理。
- 进程控制和恢复。
- 高风险操作的强制确认底线。
- 结构化动作校验。
- 日志、审计和 UI 实时事件。

依赖满足只能产生 `tasks_ready` 事件，不能由后端自动调用下一个 Agent。

## 4. 群聊路由规则

Agent Scope 就是当前群聊内所有的 Agent 群成员。

### 4.1 无活动协作任务

| 用户行为 | 路由结果 |
| --- | --- |
| 无 `@` | 交给项目Leader。 |
| 仅 `@项目Leader` | 交给项目Leader。 |
| 仅 `@一个普通 Agent` 且为问答 | 该 Agent直接回答，项目Leader被动知晓但默认不插话 |
| 仅 `@一个普通 Agent` 且要求写入 | 创建轻量单 Agent 任务，不生成多 Agent 完整计划 |

### 4.2 有活动协作任务

| 用户行为 | 路由结果 |
| --- | --- |
| 无 `@` | 高优先级交给项目Leader，判断为补充、修改、控制指令或排队新任务 |
| `@忙碌 Agent` | 项目Leader判断是否影响当前任务。相关指令可中断，无关问答排队 |

## 5. 两种协作模式

每个群聊保存自己的默认协作模式。新建群聊默认使用批准模式。

模式切换器放在消息输入框附件按钮的右侧。切换会更新该群聊的默认值，只影响尚未开始的新任务。任务创建后将实际模式固化在任务记录中。

### 5.1 批准模式

1. 项目Leader完成需求对齐。
2. 项目Leader生成完整初始计划。
3. 群聊展示项目Leader说明和结构化计划卡。
4. 用户通过按钮或自然语言批准、要求修改或取消。
5. 批准后，项目Leader开始逐项委派。

计划执行后的重大变更需要重新批准。重大变更包括以下情况。

- 扩大目标或交付范围。
- 使用原 Scope 外的 Agent。
- 引入高风险或不可逆操作。
- 显著增加时间、费用或资源消耗。
- 推翻用户已经确认的关键方案。

普通重试、顺序微调、上下文补充和 Scope 内能力等价改派不重新申请批准，但必须记录计划版本差异。

### 5.2 自动模式

1. 项目Leader完成需求对齐。
2. 项目Leader生成完整初始计划。
3. 群聊展示项目Leader说明和结构化计划卡。
4. 计划持久化并通过后端校验后，项目Leader立即开始委派。

自动模式不跳过计划展示，也不能绕过系统强制的高风险确认。

## 6. 需求对齐与计划生成

需求对齐不需要复杂动作类型。目标实现流程如下，

```
Leader 与用户自然对话
    ↓
Leader 判断需求是否已经明确
    ↓
Leader 输出最终结构化 Plan
    ↓
后端校验并保存 Plan v1
    ↓
用户批准后开始委派
```

## 7. 动态计划模型

### 7.1 初始完整计划

批准模式和自动模式都生成一份完整的最佳已知计划。计划至少包含以下信息。

```json
{
  "planId": "plan_x",
  "version": 1,
  "goal": "...",
  "mode": "approval | automatic",
  "agentScope": ["agent_a", "agent_b"],
  "tasks": [
    {
      "taskId": "task_a",
      "title": "...",
      "goal": "...",
      "assignedAgentId": "agent_a",
      "dependsOn": [],
      "acceptanceCriteria": ["..."],
      "expectedOutputs": ["..."],
      "riskLevel": "low"
    }
  ]
}
```

原始 JSON 只用于机器协议、日志和调试，不在普通群聊中直接展示。

### 7.2 版本化变更

计划执行后允许新增、删除、改派和调整依赖。

- 受影响的运行中任务需要协作式中断。
- 原版本永久保留。
- 已完成任务和证据不被覆盖。
- 下游任务基于最新有效结果重新判断。
- 项目Leader在群聊发送计划变更气泡和结构化差异卡。

### 7.3 依赖仅是事实，不是控制器

任务依赖用于以下目的。

- 表达结果消费关系。
- 计算哪些任务已满足前置条件。
- 判断变更影响范围。
- 辅助 UI 展示。
- 支持恢复和审计。

后端不得因依赖满足而自动启动任务。项目Leader收到 `tasks_ready` 后决定是否公开委派。

计划卡默认显示任务列表，每项展示负责人、前置依赖、状态和验收标准。

## 8. 委派、汇报与验收

### 8.1 委派

项目Leader每委派一个任务，都发送一条独立群聊气泡。

- 消息作者为项目Leader。
- 显式 `@具体Agent`。
- 展示人类可读的目标、约束和预期结果。
- 后台关联完整任务契约。
- 每条委派绑定唯一 `task_id` 和 `attempt_id`。
- 并行任务分别发送，不合并成一条多 Agent 气泡。

### 8.2 Agent 汇报

Agent完成、失败、阻塞、发现风险或需要协助时，立即公开汇报，不等待同批其他 Agent。

汇报气泡必须显示 `@项目Leader`。提及同时绑定项目Leader稳定 ID，不能只依赖显示名称。

汇报由自然语言总结和结构化报告卡组成。报告卡至少包含以下字段。

```text
task_id
attempt_id
status
summary
changed_files
artifacts
verification
risks
decision_required
commit
branch
worktree_status
```

### 8.3 项目Leader即时响应

项目Leader收到每份正式汇报后立即被唤醒，并在群聊中公开回复。

回复必须明确属于以下结果之一。

- 验收通过。
- 要求返工。
- 转交独立验收。
- 记录阻塞并向用户提问。
- 已通过但等待其他依赖。

项目Leader回复引用对应报告。原报告卡同步更新最终验收状态，但历史消息不可覆盖。

### 8.4 依赖就绪即调度

A 完成并通过验收后，如果 C 只依赖 A，项目Leader可以立即委派 C，无需等待无关的 B。只有同时依赖 A、B 的任务才等待两者都通过验收。

不存在固定轮次屏障。所谓阶段只能用于阅读和展示，不能成为执行推进条件。

## 9. 重试、阻塞和用户介入

### 9.1 重试

项目Leader根据失败原因决定以下动作。

- 原 Agent重试。
- 补充上下文后重试。
- 修改任务契约。
- 在 Scope 内改派。
- 请求独立验收。
- 向用户报告阻塞。

单任务默认最多 3 次执行尝试。达到硬上限后进入 `blocked`，必须向用户汇报。用户可以追加尝试、修改目标、改派或终止。

### 9.2 用户消息优先级

运行期间的新用户消息以高优先级进入项目Leader事件队列。不会无条件终止所有 Agent，项目Leader先判断影响范围，再中断相关任务。

Agent 汇报在此期间继续持久化并排队，不得丢失。

### 9.3 排队的新任务

同一群聊同一时间只允许一个活动协作任务。

若项目Leader判断新需求属于独立任务，则先保存为排队项并回复用户。排队阶段不提前生成正式计划。当前任务完成后按创建顺序自动处理，基于最新代码和上下文重新进行需求对齐。

不提供专门的队列管理 UI。用户仍可通过群聊自然语言取消或调整优先级。

## 10. Agent 上下文模型

### 10.1 独立上下文

上下文隔离单位为 `Agent × 群聊`。

- 同一 Agent在同一群聊中的多次工作回合保持连续。
- 不同群聊之间完全隔离。
- 同一 Agent在同一群聊中一次只执行一个回合。
- 新任务要求始终优先于旧记忆。

### 10.2 CLI 上下文压缩

项目Leader和普通 Agent各自 CLI 的原生会话负责上下文保持和压缩。AgentHub 不再重复维护一套自然语言滚动摘要。

### 10.3 持久化协作事实：协作黑板

CLI 会话只负责保存 Agent 的语言上下文，不能作为协作状态的唯一来源。AgentHub 为每个活动协作任务维护一份持久化的“协作黑板”，用于记录当前协作局面。

协作黑板至少包含：

- 当前协作目标和执行模式
- 当前 Agent Scope
- 当前生效的计划及其修订号
- 每个任务的负责人、依赖和当前状态
- 最近一次 Agent 报告和 Leader 验收结论
- 用户批准、关键决策和未解决问题
- 当前运行中的 Agent
- 写入任务对应的 worktree、分支和提交信息

协作黑板只保存当前有效状态，不保存完整聊天记录、模型原始输出或逐 token 的终端日志。详细历史、执行过程和工具调用保存在日志中，并通过任务、报告和消息 ID关联。

以下情况必须更新协作黑板：

- Leader 创建或修订计划
- Leader 委派、暂停、重试或取消任务
- Agent 开始执行、提交报告或报告失败
- Leader 验收、要求返工或标记阻塞
- 用户批准、修改或终止协作
- Git worktree、分支或合并状态发生变化

每次唤醒项目Leader时，系统注入当前协作黑板的精简快照，使其能够了解目标、任务进展、依赖、风险和待决策事项。详细历史由项目Leader按需查询。

应用重启、CLI 进程中断或 Leader 会话丢失后，系统以协作黑板为恢复依据，而不依赖原有 CLI 上下文继续执行。

### 10.4 群聊历史查询

所有群成员都可以搜索和读取当前群聊的完整历史，但不能跨群读取。

查询结果需要包含原始消息 ID、作者、时间、引用关系和来源。默认任务包保持精简，信息不足时 Agent自行调用查询工具。
### 10.5 可审计任务包

日志页面允许用户查看实际传给 Agent 的任务包，包括目标、约束、验收标准、工具权限、工作区、分支、依赖结果和引用消息。

系统提示词、隐藏安全规则、密钥和敏感环境变量不展示。

## 11. Git 与并行写入隔离模型

### 11.1 基本原则

worktree 只用于并行写入任务，不作为所有任务的默认执行环境。

任务创建时，项目Leader根据任务性质声明工作区模式：

```
read_only       只读任务
serial_write    串行写入任务
parallel_write  并行写入任务
```

规则如下：

- `read_only` 不创建 worktree。
- `serial_write` 使用当前协作集成工作区，同一时间只允许一个写入 Agent。
- `parallel_write` 为每个并行写入任务创建独立 worktree。
- Agent 不负责创建、分配或删除 worktree。
- worktree 只隔离文件和 Git 状态，不保存 Agent 的聊天上下文。并行任务需要的上下文由群聊历史、协作黑板和任务契约提供。

### 11.2 worktree 的创建和分配

后端 Worktree Manager 在任务正式委派前创建 worktree，并将以下信息写入任务执行记录：

```
worktree_path
branch_name
base_commit
task_id
attempt_id
```

分支和目录由系统生成，例如：

```
分支：agenthub/<collaboration_id>/<task_id>/<attempt_id>
目录：.agenthub/worktrees/<collaboration_id>/<task_id>/<attempt_id>
```

Agent 只接收后端分配的工作目录，不直接操作其他任务的 worktree。

### 11.3 只读与串行写入

只读任务可以直接使用项目工作区，但不得修改文件。

串行写入任务使用当前协作集成工作区，且必须满足：

- 同一时间最多一个写入 Agent；
- 前一个写入任务完成、失败或被中断后，才能启动下一个；
- Agent 完成后必须提交修改，或明确报告没有产生修改；
- Agent 中断或失败时，后续写入任务暂停，等待项目Leader处理残留修改；
- 系统不得静默覆盖用户已有的未提交修改。

启动串行写入前，系统必须检查工作区状态。如果存在未提交修改，应暂停任务并要求用户选择处理方式。系统不得自动删除、覆盖或隐藏这些修改。

### 11.4 并行写入与集成基线

启动并行写入前，系统创建本次协作的集成基线。

每个并行任务从同一个集成基线创建独立分支和 worktree。任务执行期间：

- Agent 只能修改自己的 worktree；
- 不同 Agent 不直接共享可变工作目录；
- Agent 必须将结果提交到自己的任务分支；
- 报告中必须包含提交、修改文件和验证结果；
- 未提交的修改不能作为已完成结果使用。

并行任务不共享 CLI 原生会话。任务所需的协作上下文通过协作黑板、群聊历史和上游任务报告注入。

### 11.5 验收、合并和冲突

项目Leader负责判断任务是否验收通过，但不负责亲自执行 Git 命令。

验收通过后，由后端 Git 合并器按顺序将任务分支合并到协作集成分支：

```
Agent 完成
    ↓
项目Leader验收
    ↓
后端自动合并
    ↓
合并成功：更新集成基线并清理 worktree
合并冲突：保留 worktree，通知项目Leader
```

合并规则如下：

- 合并操作必须串行执行；
- 无冲突时自动完成合并并记录合并提交；
- 有冲突时停止自动合并，不删除相关 worktree；
- 项目Leader决定重试、修改任务、请求用户处理或终止任务；
- 冲突解决后必须重新验收；
- 只有成功合并到协作集成分支的结果，才能作为下游任务的新代码基线。

如果多个并行任务基于同一旧基线完成，后合并的任务必须基于最新集成分支重新检查。必要时由系统要求该任务重新执行或解决冲突。

### 11.6 非 Git 工作区

如果项目工作区不是 Git 仓库：

- 只读任务可以继续执行；
- 串行写入任务可以在用户明确确认后继续；
- 并行写入任务必须先建立 Git 基线，否则不得启动。

Git 初始化、基线提交和任何远程推送都必须经过用户确认。系统不得自动配置或推送远程仓库。

### 11.7 清理

worktree 在以下条件同时满足后可以清理：

- 任务已经验收通过；
- 修改已经成功合并；
- worktree 没有未提交修改；
- 提交和合并信息已经写入协作黑板和日志。

清理时删除任务 worktree，并根据实际情况删除已合并的任务分支。以下情况不得自动清理：

- 合并冲突；
- 未提交修改；
- 任务失败但仍需保留现场；
- 用户明确要求保留。

清理操作必须记录任务、分支、worktree 路径和最终提交信息。

## 12. 进程中断与恢复

### 12.1 暂停和停止

采用分阶段终止。

1. 向运行中的 Agent发送协作式中断。
2. Agent有机会保存状态并提交中断汇报。
3. 超时仍未退出时强制终止进程。
4. 保留 worktree、修改、日志和任务状态。

“暂停”是可恢复状态，“停止或取消”是终止当前协作任务。UI 和状态模型必须明确区分。

### 12.2 应用重启

应用退出、后端重启或进程异常后，不自动继续调用 Agent。

- 恢复计划、任务、消息、上下文引用、worktree 和分支状态。
- 原运行中任务标记为 `interrupted`。
- 用户进入群聊时看到恢复提示。
- 用户点击“继续执行”后，项目Leader重新检查代码、依赖和任务状态，再决定恢复方式。

## 13. UI 交互方案

### 13.1 输入区

在附件按钮右侧放置群聊默认模式切换器。

```text
[附件] [批准模式 ▼]                    [发送]
```

模式切换只影响未来任务。

### 13.2 常驻状态条

活动协作任务存在时，在输入框正上方显示紧凑状态条。

状态条展示以下内容。

- 任务名称。
- 总体状态。
- 完成进度。
- 当前运行 Agent。
- 打开计划。

状态条提供以下常用控制。【均使用icon】

- 待批准时显示“批准”。
- 运行中显示“暂停”和“停止”。
- 中断后显示“继续”。
- 阻塞时显示“处理问题”。

不提供单个 Agent 任务的直接控制按钮。用户通过群聊自然语言要求项目Leader暂停、取消、重试或改派具体任务。

### 14.3 计划气泡

项目Leader发送普通群聊气泡，顶部为自然语言说明，内部嵌入结构化计划卡。

计划卡默认显示任务列表。每项包含负责人、依赖、状态和验收标准。原始 JSON 仅在日志或调试页面查看。

批准模式支持以下交互。

- “批准执行”按钮。
- “要求修改”按钮。
- “取消任务”按钮。
- 自然语言批准或修改。

### 14.4 计划版本 UI

- 原计划消息永久保留。
- 每次变更发送新的项目Leader气泡和差异卡。
- 最新计划卡显示当前版本号。
- 支持切换查看历史版本。
- 差异显示新增、删除、改派、依赖和验收标准变化。

### 14.5 委派、汇报和验收消息链

```text
项目Leader @Agent A 委派任务
  └─ Agent A 引用委派并 @项目Leader 汇报
       └─ 项目Leader引用汇报并给出验收结论
```

所有正式协作消息保留在群聊。启动、进度、工具调用、终端输出和重试过程进入日志页面。

### 14.6 日志页面

日志按以下层级组织。

```text
协作任务
  └─ Agent任务
       └─ 执行尝试
            ├─ 模型输出摘要
            ├─ 工具调用
            ├─ 终端输出
            ├─ Git / worktree
            └─ 状态事件
```

日志提供全局时间线，以及按 Agent、任务状态和日志类型筛选。群聊消息可跳转到对应日志，日志也可返回原始群聊消息。

不展示模型原始内部推理。只展示结构化决策、理由摘要、任务包、工具调用、进度、输出和错误。所有敏感信息必须脱敏。
