# 动态 Agent 协作模型重构方案

## 1. 文档定位

本文独立定义 AgentHub 下一代群聊协作模型的目标架构、交互规则、状态模型、权限边界、上下文机制、Git 隔离方案、数据模型和迁移路径。

本方案是一套从目标模型出发设计的根本性重构，不依赖其他方案文档作为前提。

## 2. 重构目标

新模型需要实现以下目标。

1. 项目Leader真正掌握协作决策权，而不是充当固定工作流中的计划生成节点。
2. 普通 Agent 作为项目Leader可选择调用的成员工具，但保留独立上下文和自主执行能力。
3. 用户、项目Leader和普通 Agent 的所有正式协作都发生在可见群聊中。
4. 计划可以在执行中版本化演进，不冻结为不可修改的静态 DAG。
5. 后端负责权限、持久化、状态校验、事件投递、隔离和恢复，不替项目Leader作语义决策。
6. 不同 Agent 可以并行工作，同一 Agent 在同一群聊中保持串行。
7. 所有写入任务通过 Git worktree 隔离，验收后再合并。
8. 应用重启、进程中断和计划变更后，协作事实仍可恢复和审计。

核心原则如下。

> 后端维护秩序和事实，项目Leader决定行动，普通 Agent执行并汇报，用户拥有最终意图和高风险操作的决定权。

## 3. 角色与权限

### 3.1 用户

用户拥有以下权限。

- 向群聊发送需求、补充信息和控制指令。
- 直接 `@` 任意普通 Agent。
- 同时 `@` 多个普通 Agent，限定本次协作任务的 Agent Scope。
- 在批准模式中批准、要求修改或取消计划。
- 扩大或缩小当前任务的 Agent Scope。
- 暂停、继续、停止或修改协作任务。
- 对系统规定的高风险操作进行最终确认。

### 3.2 项目Leader

第一阶段每个群聊自动包含一个固定、唯一、系统内置的项目Leader。

项目Leader拥有以下独占权限。

- 对齐用户需求。
- 判断需求是否足以生成计划。
- 生成和修改计划。
- 调用普通 Agent。
- 创建任务、返工、改派和独立验收任务。
- 验收 Agent 汇报。
- 判断哪些后续任务可以启动。
- 处理 Agent 的协助请求。
- 管理当前任务的 Agent Scope。
- 向用户提出问题或风险确认。
- 发布最终总结并结束协作任务。

第一阶段不支持把普通 Agent 提升为项目Leader，也不支持同一群聊存在多个项目Leader。内部权限模型仍应采用能力授权，为未来扩展保留空间。

### 3.3 普通 Agent

普通 Agent拥有以下能力。

- 接收用户直接消息。
- 接收项目Leader的正式委派。
- 读取当前群聊的完整历史。
- 读取工作区。
- 在被分配的 worktree 中执行写入任务。
- 向项目Leader提交完成、失败、阻塞、风险和协助请求。

普通 Agent明确不具备以下能力。

- 调用或唤醒其他普通 Agent。
- 创建下级 Agent。
- 修改协作计划。
- 扩大 Agent Scope。
- 直接结束整个协作任务。
- 绕过项目Leader请求用户批准。

普通 Agent输出中的 `@其他普通 Agent` 只是文本，不产生系统触发事件。普通 Agent需要协助时，只能 `@项目Leader` 提交 `needs_assistance`。

### 3.4 后端协调基础设施

后端不承担语义调度，只提供以下确定性能力。

- 权限检查。
- Agent Scope 校验。
- 事件队列和唤醒。
- 状态持久化。
- 任务依赖可用性计算。
- 同一 Agent 串行锁。
- Git worktree 生命周期管理。
- 进程控制和恢复。
- 高风险操作的强制确认底线。
- 结构化动作校验。
- 日志、审计和 UI 实时事件。

依赖满足只能产生 `tasks_ready` 事件，不能由后端自动调用下一个 Agent。

## 4. 群聊路由规则

### 4.1 无活动协作任务

| 用户行为 | 路由结果 |
| --- | --- |
| 无 `@` | 交给项目Leader。默认 Agent Scope 为群内全部可用普通 Agent |
| 仅 `@项目Leader` | 交给项目Leader。默认 Agent Scope 为群内全部可用普通 Agent |
| 仅 `@一个普通 Agent` 且为问答 | 该 Agent直接回答，项目Leader被动知晓但默认不插话 |
| 仅 `@一个普通 Agent` 且要求写入 | 创建轻量单 Agent 任务，不生成多 Agent 完整计划 |
| 同时 `@多个普通 Agent` | 仅项目Leader立即处理，被提及 Agent构成本次严格 Scope |
| `@项目Leader` 并 `@普通 Agent` | 交给项目Leader，被提及普通 Agent构成严格 Scope |

同时 `@多个普通 Agent` 时，消息会进入这些 Agent各自在该群的历史，但不会立即启动它们。普通 Agent必须等待项目Leader正式委派。

### 4.2 有活动协作任务

| 用户行为 | 路由结果 |
| --- | --- |
| 无 `@` | 高优先级交给项目Leader，判断为补充、修改、控制指令或排队新任务 |
| `@当前 Scope 内 Agent` | 消息直接送达该 Agent并通知项目Leader，由项目Leader判断是否影响当前计划 |
| `@Scope 外 Agent` | 用户的显式 `@` 自动把该 Agent加入当前 Scope，但不会自动启动执行 |
| `@忙碌 Agent` | 项目Leader判断是否影响当前任务。相关指令可中断，无关问答排队 |

Scope 在整个协作任务期间持续有效。任务完成后失效，不自动影响后续任务。

## 5. 两种协作模式

每个群聊保存自己的默认协作模式。新建群聊默认使用批准模式。

模式切换器放在消息输入框附件按钮的右侧。切换会更新该群聊的默认值，只影响尚未开始的新任务。任务创建后将实际模式固化在任务记录中。

### 5.1 批准模式

1. 项目Leader完成需求对齐。
2. 项目Leader生成完整初始计划。
3. 群聊展示项目Leader说明和结构化计划卡。
4. 用户通过按钮或自然语言批准、要求修改或取消。
5. 批准后，项目Leader开始逐项委派。

计划执行后的重大变更需要重新批准。重大变更包括以下情况。

- 扩大目标或交付范围。
- 使用原 Scope 外的 Agent。
- 引入高风险或不可逆操作。
- 显著增加时间、费用或资源消耗。
- 推翻用户已经确认的关键方案。

普通重试、顺序微调、上下文补充和 Scope 内能力等价改派不重新申请批准，但必须记录计划版本差异。

### 5.2 自动模式

1. 项目Leader完成需求对齐。
2. 项目Leader生成完整初始计划。
3. 群聊展示项目Leader说明和结构化计划卡。
4. 计划持久化并通过后端校验后，项目Leader立即开始委派。

自动模式不跳过计划展示，也不能绕过系统强制的高风险确认。

### 5.3 单 Agent 轻量写入任务

用户明确 `@某个普通 Agent` 并要求修改工作区时，用户的指令本身构成任务授权。

- 不生成多 Agent 完整计划。
- 不因批准模式再次要求用户批准。
- 创建正式任务记录、独立 worktree 和执行尝试。
- Agent完成后公开 `@项目Leader` 汇报。
- 项目Leader验收后触发合并。
- 高风险或不可逆操作仍需确认。
- 需要其他 Agent时，由项目Leader决定是否升级为完整协作任务。

## 6. 需求对齐与计划生成

### 6.1 一次只问一个问题

项目Leader每轮只询问一个当前最关键的阻塞问题。收到回答后重新评估，不预先机械播放问题清单。

可采用合理默认值的信息不应反复询问。所采用的假设必须在计划中明确展示。

### 6.2 由项目Leader判断何时可以规划

不要求用户明确发送“需求确认完毕”。项目Leader根据目标、交付物、约束、风险和验收条件判断是否已经足够。

项目Leader可自行读取和调研代码库。第一阶段不引入正式计划前的普通 Agent侦察任务。

### 6.3 结构化动作批次

项目Leader每个回合输出结构化动作批次，而不是由后端从自由文本猜测控制意图。

一个回合可以并行委派多个 Agent，也可以处理多份已到达报告。需求对齐阶段的 `ask_user` 完全互斥。执行阶段若一条任务链需要用户决策，仅阻塞受影响链，项目Leader仍可推进无关任务。

建议的动作类型如下。

```text
reply
ask_user
create_plan
revise_plan
request_plan_approval
delegate_task
accept_report
request_retry
request_independent_review
pause_task_chain
interrupt_run
complete_run
queue_followup
```

## 7. 动态计划模型

### 7.1 初始完整计划

批准模式和自动模式都生成一份完整的最佳已知计划。计划至少包含以下信息。

```json
{
  "planId": "plan_x",
  "version": 1,
  "goal": "...",
  "mode": "approval | automatic",
  "agentScope": ["agent_a", "agent_b"],
  "tasks": [
    {
      "taskId": "task_a",
      "title": "...",
      "goal": "...",
      "assignedAgentId": "agent_a",
      "dependsOn": [],
      "acceptanceCriteria": ["..."],
      "expectedOutputs": ["..."],
      "riskLevel": "low"
    }
  ]
}
```

原始 JSON 只用于机器协议、日志和调试，不在普通群聊中直接展示。

### 7.2 版本化变更

计划执行后允许新增、删除、改派和调整依赖。每次修改创建不可变的新版本。

- 原版本永久保留。
- 已完成任务和证据不被覆盖。
- 受影响的结果可标记为 `stale` 或 `superseded`。
- 受影响的运行中任务需要协作式中断。
- 下游任务基于最新有效结果重新判断。
- 项目Leader在群聊发送计划变更气泡和结构化差异卡。

### 7.3 依赖仅是事实，不是控制器

任务依赖用于以下目的。

- 表达结果消费关系。
- 计算哪些任务已满足前置条件。
- 判断变更影响范围。
- 辅助 UI 展示。
- 支持恢复和审计。

后端不得因依赖满足而自动启动任务。项目Leader收到 `tasks_ready` 后决定是否公开委派。

计划卡默认显示任务列表，每项展示负责人、前置依赖、状态和验收标准。

## 8. 委派、汇报与验收

### 8.1 委派

项目Leader每委派一个任务，都发送一条独立群聊气泡。

- 消息作者为项目Leader。
- 显式 `@具体Agent`。
- 展示人类可读的目标、约束和预期结果。
- 后台关联完整任务契约。
- 每条委派绑定唯一 `task_id` 和 `attempt_id`。
- 并行任务分别发送，不合并成一条多 Agent 气泡。

### 8.2 Agent 汇报

Agent完成、失败、阻塞、发现风险或需要协助时，立即公开汇报，不等待同批其他 Agent。

汇报气泡必须显示 `@项目Leader`。提及同时绑定项目Leader稳定 ID，不能只依赖显示名称。

汇报由自然语言总结和结构化报告卡组成。报告卡至少包含以下字段。

```text
task_id
attempt_id
status
summary
changed_files
artifacts
verification
risks
decision_required
commit
branch
worktree_status
```

### 8.3 项目Leader即时响应

项目Leader收到每份正式汇报后立即被唤醒，并在群聊中公开回复。

回复必须明确属于以下结果之一。

- 验收通过。
- 要求返工。
- 转交独立验收。
- 记录阻塞并向用户提问。
- 已通过但等待其他依赖。

项目Leader回复引用对应报告。原报告卡同步更新最终验收状态，但历史消息不可覆盖。

### 8.4 风险分级验收

- 普通低风险任务由项目Leader直接验收。
- 高风险、跨模块、关键交付或超出项目Leader专业判断范围的任务，委派独立 Agent验收。
- 实现者不能验收自己的工作。
- 验收 Agent必须位于当前 Scope。
- Scope 中没有合适验收者时，项目Leader向用户申请扩大 Scope，或明确说明只能进行有限验收。

### 8.5 依赖就绪即调度

A 完成并通过验收后，如果 C 只依赖 A，项目Leader可以立即委派 C，无需等待无关的 B。只有同时依赖 A、B 的任务才等待两者都通过验收。

不存在固定轮次屏障。所谓阶段只能用于阅读和展示，不能成为执行推进条件。

## 9. 重试、阻塞和用户介入

### 9.1 重试

项目Leader根据失败原因决定以下动作。

- 原 Agent重试。
- 补充上下文后重试。
- 修改任务契约。
- 在 Scope 内改派。
- 请求独立验收。
- 向用户报告阻塞。

单任务默认最多 3 次执行尝试。达到硬上限后进入 `blocked`，必须向用户汇报。用户可以追加尝试、修改目标、改派或终止。

### 9.2 局部等待

某个任务需要用户决策时，仅暂停该任务和受影响的下游任务。无关任务继续运行。项目Leader立即向用户提出一个最关键问题。

### 9.3 用户消息优先级

运行期间的新用户消息以高优先级进入项目Leader事件队列。不会无条件终止所有 Agent，项目Leader先判断影响范围，再中断相关任务。

Agent 汇报在此期间继续持久化并排队，不得丢失。

### 9.4 排队的新任务

同一群聊同一时间只允许一个活动协作任务。

若项目Leader判断新需求属于独立任务，则先保存为排队项并回复用户。排队阶段不提前生成正式计划。当前任务完成后按创建顺序自动处理，基于最新代码和上下文重新进行需求对齐。

不提供专门的队列管理 UI。用户仍可通过群聊自然语言取消或调整优先级。

## 10. Agent 上下文模型

### 10.1 独立上下文

上下文隔离单位为 `Agent × 群聊`。

- 同一 Agent在同一群聊中的多次工作回合保持连续。
- 不同群聊之间完全隔离。
- 同一 Agent在同一群聊中一次只执行一个回合。
- 新任务要求始终优先于旧记忆。

### 10.2 CLI 上下文压缩

项目Leader和普通 Agent各自 CLI 的原生会话负责上下文保持和压缩。AgentHub 不再重复维护一套自然语言滚动摘要。

### 10.3 持久化协作事实

CLI 上下文不能作为协作真相源。以下事实必须持久化到 AgentHub 数据库。

- 当前协作目标。
- 执行模式。
- Agent Scope。
- 计划版本。
- 任务、依赖和状态。
- 用户审批和关键决策。
- Agent 报告。
- 项目Leader验收。
- Git worktree、分支和提交。
- 未解决问题。

每次唤醒项目Leader时，注入一份当前状态快照。详细历史通过工具按需读取。

### 10.4 群聊历史查询

所有群成员都可以搜索和读取当前群聊的完整历史，但不能跨群读取。

查询结果需要包含原始消息 ID、作者、时间、引用关系和来源。默认任务包保持精简，信息不足时 Agent自行调用查询工具。
```

### 10.5 可审计任务包

日志页面允许用户查看实际传给 Agent 的任务包，包括目标、约束、验收标准、工具权限、工作区、分支、依赖结果和引用消息。

系统提示词、隐藏安全规则、密钥和敏感环境变量不展示。

## 11. Git worktree 协作模型

### 11.1 隔离原则

所有写入任务使用独立 Git worktree 和任务分支。不同 Agent可以并行写入，不直接共享可变工作目录。

只读问答和只读检查不要求创建 worktree。

### 11.2 非 Git 工作区

首次需要写入协作时，如果工作区不是 Git 仓库，系统向用户请求一次性确认。确认后执行本地 Git 初始化并创建基线提交，不自动配置或推送远程仓库。

### 11.3 未提交修改

启动协作前必须检测主工作区未提交修改。系统不得忽略或静默覆盖。安全实现应要求用户显式选择创建本地安全基线或先自行处理，再继续创建 worktree。

### 11.4 分支与合并

- 每个任务从当前协作集成基线创建分支和 worktree。
- 验收通过后，系统自动尝试合并到本次协作任务的集成分支。
- 无冲突时完成自动合并并记录提交。
- 有冲突时停止自动合并并通知项目Leader。
- 项目Leader从当前 Scope 中委派合适 Agent解决冲突。
- 冲突解决结果仍需验收。
- 只有成功合并的结果才能成为下游任务的新基线。

### 11.5 清理

协作取消或完成后，worktree 不立即删除。

- 已合并且无额外修改的 worktree 默认保留 7 天后自动清理。
- 未合并修改、冲突状态或用户标记保留的 worktree 不自动删除。
- 详情页允许查看、立即清理或延长保留。
- 清理操作写入日志。

## 12. 进程中断与恢复

### 12.1 暂停和停止

采用分阶段终止。

1. 向运行中的 Agent发送协作式中断。
2. Agent有机会保存状态并提交中断汇报。
3. 超时仍未退出时强制终止进程。
4. 保留 worktree、修改、日志和任务状态。

“暂停”是可恢复状态，“停止或取消”是终止当前协作任务。UI 和状态模型必须明确区分。

### 12.2 应用重启

应用退出、后端重启或进程异常后，不自动继续调用 Agent。

- 恢复计划、任务、消息、上下文引用、worktree 和分支状态。
- 原运行中任务标记为 `interrupted`。
- 用户进入群聊时看到恢复提示。
- 用户点击“继续执行”后，项目Leader重新检查代码、依赖和任务状态，再决定恢复方式。

## 13. 风险与审批底线

风险控制由系统规则和项目Leader判断共同组成。

后端强制确认的操作至少包括以下类别。

- 大量删除文件。
- 覆盖未提交修改。
- 初始化 Git 仓库。
- 推送远程仓库。
- 发布或部署。
- 付费调用或购买行为。
- 向外部人员或服务发送消息。
- 读取、写入或暴露密钥。
- 其他不可逆或明显越权操作。

项目Leader可以把其他操作升级为需要确认，但不能降低系统底线风险等级。

## 14. UI 交互方案

### 14.1 输入区

在附件按钮右侧放置群聊默认模式切换器。

```text
[附件] [批准模式 ▼]                    [发送]
```

模式切换只影响未来任务。

### 14.2 常驻状态条

活动协作任务存在时，在输入框正上方显示紧凑状态条。

状态条展示以下内容。

- 任务名称。
- 总体状态。
- 完成进度。
- 当前运行 Agent。
- 等待用户事项。
- 打开计划。
- 打开日志。

状态条提供以下常用控制。

- 待批准时显示“批准”。
- 运行中显示“暂停”和“停止”。
- 中断后显示“继续”。
- 阻塞时显示“处理问题”。

不提供单个 Agent任务的直接控制按钮。用户通过群聊自然语言要求项目Leader暂停、取消、重试或改派具体任务。

### 14.3 计划气泡

项目Leader发送普通群聊气泡，顶部为自然语言说明，内部嵌入结构化计划卡。

计划卡默认显示任务列表。每项包含负责人、依赖、状态和验收标准。原始 JSON 仅在日志或调试页面查看。

批准模式支持以下交互。

- “批准执行”按钮。
- “要求修改”按钮。
- “取消任务”按钮。
- 自然语言批准或修改。

自然语言最终必须落成明确的结构化审批事件。

### 14.4 计划版本 UI

- 原计划消息永久保留。
- 每次变更发送新的项目Leader气泡和差异卡。
- 最新计划卡显示当前版本号。
- 支持切换查看历史版本。
- 差异显示新增、删除、改派、依赖和验收标准变化。

### 14.5 委派、汇报和验收消息链

```text
项目Leader @Agent A 委派任务
  └─ Agent A 引用委派并 @项目Leader 汇报
       └─ 项目Leader引用汇报并给出验收结论
```

所有正式协作消息保留在群聊。启动、进度、工具调用、终端输出和重试过程进入日志页面。

### 14.6 日志页面

日志按以下层级组织。

```text
协作任务
  └─ Agent任务
       └─ 执行尝试
            ├─ 模型输出摘要
            ├─ 工具调用
            ├─ 终端输出
            ├─ Git / worktree
            └─ 状态事件
```

日志提供全局时间线，以及按 Agent、任务状态和日志类型筛选。群聊消息可跳转到对应日志，日志也可返回原始群聊消息。

不展示模型原始内部推理。只展示结构化决策、理由摘要、任务包、工具调用、进度、输出和错误。所有敏感信息必须脱敏。

### 15.4 关键状态不变量

1. `waiting_user` 的需求对齐回合不能同时创建计划。
2. 普通 Agent不能创建委派事件。
3. Agent不在当前 Scope 时不能被项目Leader调用。
4. 同一 Agent在同一群聊中最多有一个活动回合。
5. 未通过验收的结果不能供下游任务消费。
6. 未成功合并的写入结果不能成为下游代码基线。
7. 只有项目Leader能把协作任务标记为 `completed`。
8. 后端不能因任务 `ready` 自动调用 Agent。
9. 高风险系统确认点不能被自动模式绕过。


## 16. 旧系统处置

本次不保留旧执行兼容层。

### 18.1 删除

- 旧静态 DAG Scheduler。
- 旧冻结 Plan 执行入口。
- 旧 `approve_plan` 驱动的唯一执行路径。
- Phase 完成后自动释放下一 Phase 的逻辑。
- 后端自动启动 Ready Task 的逻辑。
- 旧 Execution 主状态 JSON 快照。
- 消息 metadata 作为协作真相源的实现。
- 旧前端执行面板状态机和轮询逻辑。
- Legacy DAG、chain、mini collaboration 等执行分支。

### 18.2 旧数据

- 已完成旧记录保留为只读历史。
- 未完成旧执行统一标记为旧版中断。
- 不把旧执行转换并继续运行。
- 用户可以基于旧消息创建新的后续任务。
- 只提供最小归档读取，不提供旧执行 API 兼容。


## 20. 测试策略

### 20.1 权限测试

- 普通 Agent无法调用其他 Agent。
- 非 Scope Agent无法被项目Leader调用。
- 用户 `@Scope 外 Agent` 后 Scope 正确扩展。
- 普通 Agent文本中的 `@Agent` 不产生触发。

### 20.2 状态机测试

- `ask_user` 回合不能创建计划。
- 未批准计划不能在批准模式执行。
- 自动模式计划展示并持久化后才能委派。
- 后端不能自动启动 Ready Task。
- 只有项目Leader能完成整个 Run。

### 20.3 并发测试

- A、B 独立并行。
- A 先完成时立即汇报和验收。
- C 只依赖 A 时不等待 B。
- 同一 Agent多个任务正确排队。
- 项目Leader事件回合串行且不丢事件。

### 20.4 计划变更测试

- 新增、删除、改派和依赖变更产生新版本。
- 重大变更在批准模式重新等待批准。
- 受影响下游正确标记 stale。
- 无关任务继续运行。

### 20.5 Git 测试

- 非 Git 初始化确认。
- 并行 worktree 隔离。
- 自动无冲突合并。
- 冲突后停止并通知项目Leader。
- 未合并修改不被自动清理。

### 20.6 恢复测试

- 后端重启后恢复事件、任务和 worktree。
- 原运行任务标记 interrupted。
- 用户点击继续后由项目Leader重新决策。
- 不发生无人值守自动恢复执行。

### 20.7 UI 测试

- 模式切换位置和持久化。
- 状态条各状态和控制。
- 计划审批按钮和自然语言审批。
- 计划版本差异。
- 委派、汇报、验收引用链。
- 日志和群聊双向跳转。

## 21. 完成标准

重构只有在以下条件全部满足时才算完成。

- 项目Leader是唯一拥有 Agent 调用权限的 Agent。
- 普通 Agent无法通过任何入口调用其他 Agent。
- 需求确认回合不会再同时生成 `plan_json`。
- 批准模式和自动模式均可按群聊配置。
- 自动模式仍展示完整初始计划。
- 计划支持版本化动态修改。
- 所有委派、报告和验收在群聊公开可追踪。
- Agent报告明确 `@项目Leader`。
- 后端不自动执行依赖已满足的后续任务。
- A 完成后可推动只依赖 A 的 C，无需等待 B。
- 同一 Agent串行，不同 Agent可并行。
- 所有写入任务使用独立 Git worktree。
- 结果验收后才允许合并和供下游消费。
- 应用重启后可恢复，但不会自动继续调用 Agent。
- 日志不展示隐藏思维链，任务包可审计且敏感信息脱敏。
- 新系统不存在旧 Scheduler、旧写入 API 和双状态机。
- 旧协作记录仅作为只读历史存在。

## 22. 最终架构定义

新模型可以概括为以下一句话。

> 以固定项目Leader为唯一调度者，以普通 Agent为具备独立上下文的可调用成员，以公开群聊消息作为协作界面，以版本化计划和持久化事件作为事实记录，以 Git worktree作为并行写入隔离，由项目Leader在每个关键事件后动态决定下一步。
