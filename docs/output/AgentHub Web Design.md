# AgentHub Web Design

这是一份可迁移的 Web 工作台 UI/UX 风格文档。它来自 AgentHub 的界面优化经验，但不只服务于 AgentHub。任何需要构建“长期使用、信息密集、多对象切换、带资源/上下文/操作区”的 Web 产品，都可以把这份文档作为界面复现与风格迁移标准。

目标不是复制某一个页面，而是复现一种专业工作台气质：稳定、克制、高密度、上下文连续、组件一致、深浅色主题都成立。

适用产品包括：AI Agent 工作台、开发者工具、在线 IDE、CRM、项目管理、运维控制台、数据分析平台、内容生产后台、资源管理系统、团队协作工具。

## 1. 使用方式

### 1.1 先映射业务，再套用界面

不要直接把“对话、项目、资源管理器”照搬到所有产品。先把你的业务拆成以下 5 个槽位，再套用工作台骨架。

1. `Activity`：用户频繁切换的一级工作入口，例如对话、客户、工单、项目、报表、资源、团队。
2. `Context List`：当前 Activity 下的对象列表，例如会话列表、客户列表、工单列表、文件夹列表。
3. `Workspace`：用户完成主要工作的区域，例如聊天、编辑器、表格、看板、详情页、画布。
4. `Dock / Inspector`：辅助上下文区域，例如文件、预览、属性、日志、版本、评论、权限。
5. `Command Area`：输入、搜索、批量操作、执行按钮、AI 指令或快捷命令区域。

AgentHub 中的对应关系：

1. `ActivityRail` 对应 `Activity`。
2. `ActivityPanel` 对应 `Context List`。
3. `WorkspaceFrame` 对应 `Workspace`。
4. `OptionalDock` 对应 `Dock / Inspector`。
5. `Composer / Toolbar` 对应 `Command Area`。

### 1.2 风格迁移原则

迁移到新业务时，保持骨架和交互逻辑不变，替换业务对象、图标、命名和信息层级。

1. AI Agent 产品：Activity 可以是对话、Agent、项目、资源、团队。
2. CRM 产品：Activity 可以是客户、线索、商机、任务、团队。
3. DevTool 产品：Activity 可以是文件、搜索、版本、运行、插件、环境。
4. 数据平台：Activity 可以是数据源、报表、仪表盘、任务、权限。
5. 运维平台：Activity 可以是服务、告警、日志、部署、成员。

任何业务都应遵守同一个问题：用户此刻正在处理什么对象，围绕这个对象需要哪些上下文，哪些操作应该内联完成。

## 2. 总体设计原则

### 2.1 工作台优先，而不是页面拼装

主界面应被设计成一个稳定工作台，不是多个独立卡片的集合。

必须做到：

1. 主界面有稳定外壳，包括一级导航、上下文面板、主工作区、辅助 dock、命令/输入区。
2. 一级导航与展开面板在视觉上是一体的，而不是按钮栏外加浮动卡片。
3. 主工作区被外层工作台区域包裹，像专业软件的 canvas/editor，而不是临时拼起来的 demo。
4. 文件、对话、客户、项目、团队、设置等能力属于同一个工作台系统，视觉和交互语言必须统一。

禁止：

1. 页面上到处漂浮孤立卡片。
2. 用大面积阴影制造层级。
3. 每个功能都做成弹窗，导致用户离开当前上下文。
4. 把生产力界面做成营销页、仪表盘模板或 demo 组件集合。

### 2.2 稳定骨架先于装饰

商业级产品的第一感受来自稳定骨架，而不是花哨视觉。

规范：

1. 推荐骨架：`ActivityRail + ActivityPanel + WorkspaceFrame + OptionalDock + CommandArea`。
2. ActivityRail 宽度稳定，推荐 `52-60px`。
3. ActivityPanel 宽度稳定，推荐 `280-320px`，收起时宽度为 `0`，工作区自然扩展。
4. 工作区四周保留呼吸空间，推荐上/下/右 `12-16px`，面板与工作区间距 `10-16px`。
5. 工作区使用统一圆角和边框，推荐圆角 `18-22px`，边框 `1px`。
6. 工作区内部头部、内容区、输入区共享同一背景系统，不使用割裂的渐变或厚重卡片。

### 2.3 信息密度要专业，不要稀疏

生产力产品不是宣传页。列表、工具栏、面板需要适合反复使用和快速扫描。

规范：

1. 项目列表、对话列表、成员列表、客户列表、工单列表采用紧凑行高。
2. 行间距推荐 `2-6px`，不要用大卡片间距。
3. 标题字号控制在 `13-15px`，工作台面板内不要使用 hero 级字体。
4. 次级信息使用 `11-12px`，颜色降低对比，但必须可读。
5. hover 态用于提示可操作区域，不能导致布局抖动。

### 2.4 上下文连续，而不是频繁跳转

成熟工作台的交互核心是让用户留在当前上下文里完成任务。

规范：

1. 能内嵌展示的内容，优先在 WorkspaceFrame 内切换或 dock 展开。
2. 能原地完成的操作，优先内联完成。
3. 弹窗只用于大体量表单、跨上下文设置、复杂冲突解决、高风险流程。
4. 切换一级入口时，工作区状态要尽量保留，避免用户丢失正在处理的对象。

## 3. 布局规范

### 3.1 ActivityRail

ActivityRail 是产品的一级导航，不是普通 sidebar。

结构：

1. 顶部：产品 logo。
2. 中部：核心工作入口，如对话、搜索、项目、资源、好友、团队、客户、工单、报表。
3. 底部：工作空间、主题、用户。

视觉：

1. 背景透明或与外层底色一致。
2. 按钮默认无边框、无发光、无装饰条。
3. 激活态只改变 icon 实心/颜色和轻量背景。
4. 用户头像按钮单独设计，允许更精致的头像、在线点、圆角，但不能破坏统一尺寸。
5. icon 使用统一图标库，优先 `lucide-react`；同一产品内不要混用不同风格图标。

行为：

1. 点击主入口展开对应 ActivityPanel。
2. 再次点击当前入口可收起面板，让工作区完全展开。
3. 工作空间、主题、用户这类全局入口不应渲染左侧大面板。
4. 工作空间适合用浮层选择个人空间/团队空间。
5. 主题适合直接切换，不打开多余面板。
6. 用户适合用浮层展示资料、设置、退出登录。

### 3.2 ActivityPanel

ActivityPanel 是一级导航的展开态，必须与 ActivityRail 视觉一体。

规范：

1. ActivityRail 和 ActivityPanel 使用同一背景色，中间不加分隔线。
2. ActivityPanel 不做卡片，不加独立阴影。
3. 面板顶部统一使用 `PanelHeader`。
4. `eyebrow` 表示场景说明。
5. `title` 表示当前对象，例如项目、对话、客户、工单。
6. `description` 表示对象数量、状态或范围。
7. `actions` 放新建、刷新、导入等主要动作。
8. 如果需要搜索框，需要固定在头部下方，避免不同面板搜索位置漂移。
9. 如果有新建按钮，放在面板顶部栏右侧，使用强对比 icon。
10. 可折叠内容必须有动画，推荐 `grid-template-rows` 或 height transition，禁止瞬间跳变。

业务迁移示例：

1. AI 产品：Panel 展示会话、Agent、项目。
2. CRM：Panel 展示客户、商机、联系人分组。
3. 运维：Panel 展示服务、环境、告警分组。
4. 数据平台：Panel 展示报表、数据源、任务分组。

### 3.3 WorkspaceFrame

WorkspaceFrame 是主要生产区域，视觉上应像被外层工作台区域包裹的工作区卡片。

规范：

1. 外层区域颜色：ActivityPanel、工作区上/下/右侧剩余区域必须统一。
2. 工作区背景色：深色与浅色主题分别独立定义，不使用渐变。
3. 工作区必须有边框，浅色主题推荐 `#dfe3ea`，深色主题推荐 `rgba(255,255,255,0.12-0.16)`。
4. 工作区头部背景与工作区内容背景一致。
5. 工作区内部不要再套一层页面大卡片。
6. 工作区应承载当前业务的主任务，例如聊天、编辑、审批、表格、详情、画布、预览。

### 3.4 OptionalDock

Dock 是工作区内部的辅助上下文，不是外部弹窗。

规范：

1. 能内嵌展示的资源、文件、资产、预览、日志、属性、评论、设置页，优先在 WorkspaceFrame 内切换或 dock 展开。
2. Dock 顶部与主工作区头部垂直对齐。
3. Dock 头部排版使用：`icon + 当前对象名称 + 数量/状态`。
4. 避免“项目资源管理器”这类冗长标题，优先展示当前对象名称。
5. Dock 头部下方必须有 `1px` border。
6. Dock 支持展开/折叠，折叠时释放工作区宽度。
7. 列表底部不要放无意义说明，如“云端·0文件”。

业务迁移示例：

1. 开发工具：Dock 是文件树、预览、终端、版本记录。
2. CRM：Dock 是客户资料、活动记录、合同附件。
3. 数据平台：Dock 是字段、血缘、筛选器、任务日志。
4. 运维平台：Dock 是日志、指标、事件、部署详情。

## 4. 主题与颜色规范

### 4.1 深色主题

深色主题目标是“安静、专注、专业”，不是纯黑炫酷。

建议：

1. 外层底色：接近 `#171716`，用于 ActivityPanel 和工作区外侧。
2. 工作区底色：接近 `#080807` 或同级深色。
3. 面板 hover：白色透明度 `6-8%`。
4. 激活态：白色透明度 `10-12%`。
5. 边框：白色透明度 `10-16%`。
6. 菜单背景：深色半透明，推荐 `90%` 左右不透明度，配合 blur。

避免：

1. 大面积纯黑导致层级丢失。
2. 高饱和紫蓝渐变铺满界面。
3. 大面积发光、描边、霓虹效果。

### 4.2 浅色主题

浅色主题不能只是把深色变白。浅色主题尤其要解决“外层白边”和“卡片悬浮感过强”的问题。

建议：

1. App 外层底色、ActivityPanel 底色、工作区外侧剩余区域必须统一，推荐 `#eef1f5`。
2. 工作区底色推荐 `#ffffff`。
3. 工作区边框推荐 `#dfe3ea`。
4. hover 背景推荐 `#f5f6f8`。
5. 激活态推荐 `#f0f2f5`。
6. 菜单背景用 `rgba(255,255,255,0.9)`，避免厚重纯白浮层。

验收标准：

1. 浅色主题下，ActivityPanel 外侧、工作区上方、下方、右侧空白必须是同一颜色。
2. 工作区白色卡片应被外层浅灰背景包裹，而不是整页白底上漂一块白卡。
3. Dock、主工作区、输入区的头部背景必须与对应工作区背景一致。

### 4.3 颜色 token

所有组件必须使用语义 token，而不是散落硬编码颜色。

推荐 token：

1. `--app-bg`：页面最外层背景。
2. `--activity-zone-bg`：ActivityRail、ActivityPanel、工作区外侧背景。
3. `--workspace-frame-bg`：主工作区背景。
4. `--workspace-frame-border`：主工作区边框。
5. `--panel-bg`：面板背景。
6. `--activity-hover`：列表/按钮 hover。
7. `--activity-selected`：列表/按钮选中。
8. `--activity-subtle`：轻量按钮和输入底色。
9. `--menu-bg`：菜单背景。
10. `--danger` / `--danger-soft`：危险操作。

### 4.4 行业迁移色彩

不同业务可以换品牌色，但不能破坏工作台的中性骨架。

1. AI/开发者工具：可使用低饱和蓝、青、绿作为状态色，主界面仍以中性色为底。
2. CRM/销售：可使用蓝、绿、琥珀表达客户状态，但不要让列表变成彩色标签墙。
3. 数据/BI：可让图表承担色彩表达，导航和工作台保持克制。
4. 运维/安全：危险、警告、成功颜色必须语义明确，避免装饰性色彩干扰告警判断。
5. 内容生产：可略微增加封面/预览区域的视觉表现，但工具栏和列表仍保持专业密度。

## 5. 组件规范

### 5.1 按钮

通用按钮规范：

1. 工具型按钮优先 icon-only。
2. 不用文字按钮表达常见工具动作，如新建、折叠、更多、刷新、下载、关闭。
3. 所有 icon-only 按钮必须提供 `aria-label` 和 `title`。
4. 默认按钮不要加边框和阴影。
5. hover 只做轻量背景和颜色变化。
6. active 可用 `scale(0.96)` 以内的轻微反馈。
7. 所有“+”使用圆圈包裹的加号 icon，例如 `CirclePlus` 或 `PlusCircle`。

### 5.2 Icon

规范：

1. 使用同一图标库，默认 `lucide-react`。
2. 主导航 icon 默认线性，激活时允许 `fill: currentColor` 形成实心感。
3. 不同入口必须使用可区分图标。
4. 好友/成员使用用户或联系人图标。
5. 团队/组织使用组织、多成员、Building 图标，不与好友重复。
6. 项目/资源使用文件夹、项目、仓库、资产图标。
7. Dock 入口图标要与对应业务对象保持一致。
8. ActivityRail icon 推荐 `18-20px`。
9. 面板动作 icon 推荐 `18-21px`。
10. 列表行内操作 icon 推荐 `13-16px`。

### 5.3 菜单与下拉

菜单是专业感的高频细节，必须统一。

规范：

1. 所有“更多”菜单、下拉框、浮层层级必须高于工作区、dock、输入框，推荐 `z-index >= 1500`。
2. 菜单宽度自适应文本，避免固定大宽度造成空白。
3. 菜单最小宽度推荐 `104-132px`，最大宽度推荐 `240-280px`。
4. 菜单背景适度透明，深浅色主题都推荐 `80-90%` 不透明度。
5. 菜单开启位置要自动避让视口边界。
6. 底部按钮触发的浮层应出现在按钮上方，并完整显示。
7. 菜单关闭逻辑必须支持点击外部关闭、点击触发按钮再次关闭、选择动作后关闭。

禁止：

1. 菜单被工作区、资源管理器、输入框遮挡。
2. 菜单宽度远大于文本。
3. 多个菜单组件各写一套视觉样式。

### 5.4 列表行

列表是工作台的信息主载体。

规范：

1. 行本身是点击目标，右侧操作按钮只在 hover/focus/active 时显示。
2. 行内主文本不要全部加粗；只在确实需要强调时使用 `font-semibold`。
3. 项目名、客户名、文件夹名默认 `font-normal`。
4. 对话、工单、任务、客户列表主标题下方应展示最近消息、状态、摘要或下一步动作。
5. 时间使用短格式：`刚刚`、`3分钟前`、`2小时前`、`5天前`、`2周前`。
6. hover 态改变背景，不改变尺寸。
7. 激活态背景轻量，不加左侧装饰条、边框或发光。

业务迁移示例：

1. 对话列表：标题 + 最近一条消息 + 时间。
2. 客户列表：客户名 + 当前阶段/最近跟进 + 时间。
3. 工单列表：问题标题 + 状态/负责人 + 时间。
4. 文件列表：文件名 + 类型/大小/修改时间。

### 5.5 表单与输入

规范：

1. 搜索框位置稳定，优先放在 PanelHeader 下方。
2. 输入底色使用 `activity-subtle`，不要用强边框。
3. 表单在浮层中要紧凑，不要做完整页面级表单。
4. Enter 可提交的输入必须处理空值和 loading 禁用态。
5. 角色、权限、主题等有限选项使用 select、segmented control、menu，不要使用自由文本。

### 5.6 Toolbar

Toolbar 是工作区的高频操作层。

规范：

1. 工具栏紧贴当前工作对象，不要漂浮在页面任意位置。
2. 常用操作使用 icon-only，危险或不可逆操作可以使用文字确认。
3. 工具栏按钮尺寸稳定，hover 不导致布局变化。
4. 分组用间距或细分隔表达，不用厚边框卡片包裹。
5. 工具栏应在不同业务中保持相同操作语法：新建、刷新、筛选、排序、更多、关闭。

## 6. 交互规范

### 6.1 内联优先，弹窗克制

能在原地完成的操作，不使用弹窗。

优先内联的场景：

1. 重命名项目、对话、客户、工单、文件。
2. 删除二次确认。
3. 归档、置顶、免打扰、标记状态。
4. 团队成员角色调整。
5. 展开/折叠列表。
6. Dock 内容展示。

允许弹窗的场景：

1. 大体量表单。
2. 跨上下文设置页。
3. 文件上传、复杂冲突解决。
4. 用户必须专注处理且不能误触的高风险流程。

### 6.2 折叠与动画

规范：

1. 所有可折叠组件必须有折叠动画。
2. 折叠动画时间推荐 `160-240ms`。
3. 使用 `cubic-bezier(0.16, 1, 0.3, 1)` 一类自然缓动。
4. 折叠时内容不应溢出或遮挡其他区域。
5. 展开/收起不能改变同级按钮尺寸。

### 6.3 状态反馈

规范：

1. loading 不用大弹窗，优先 skeleton 或按钮内 spinner。
2. 成功反馈使用 toast，避免阻断操作。
3. 失败反馈在操作附近展示，toast 可辅助说明。
4. 删除确认使用原地二次点击，不默认弹 modal。
5. disabled 状态必须有视觉变化和 title 说明。

### 6.4 层级与遮挡

规范：

1. 工作区 `z-index` 保持低层级。
2. dock、header、composer 只在自身区域内建立层级。
3. 浮层菜单使用 portal 到 `document.body`。
4. 所有菜单统一高层级，避免被 Dock、输入框、文件树、预览面板遮挡。
5. 浮层需要监听 resize/scroll 并重新定位。

## 7. 响应式规范

### 7.1 桌面端

桌面端是该风格的主要形态。

规范：

1. ActivityRail 固定在最左侧。
2. ActivityPanel 可展开/收起。
3. WorkspaceFrame 占据主区域。
4. OptionalDock 从工作区内部右侧展开。
5. 输入区或命令区固定在工作区底部或当前对象附近。

### 7.2 平板与窄屏

规范：

1. ActivityRail 可以变为顶部横向栏。
2. ActivityPanel 可以变为顶部下拉式区域或覆盖式面板。
3. OptionalDock 不再挤压主工作区，应改为覆盖式面板。
4. 横向按钮区允许滚动，但不能压缩 icon 尺寸到不可点击。
5. 主工作区保持最小可用高度，不被面板挤到失效。

### 7.3 移动端

该风格可以迁移到移动端，但不应机械缩小桌面布局。

规范：

1. 一级入口保留，但可改为底部 tab 或顶部工具条。
2. Context List 与 Workspace 通常分屏显示，而不是强行并排。
3. Dock 变为全屏抽屉或底部 sheet。
4. 高频操作保留 icon，低频操作收进菜单。
5. 输入区必须始终可达，并避让系统键盘。

## 8. 视觉细节规范

### 8.1 阴影

规范：

1. 主工作台少用阴影，主要依靠背景差异、边框、间距建立层级。
2. 菜单/浮层允许轻阴影，推荐 `0 12px 28px rgba(0,0,0,0.18-0.24)`。
3. 工作区大卡片阴影要克制，浅色主题尤其避免“漂浮卡片 demo 感”。

### 8.2 边框

规范：

1. 工作区外框必须有 `1px` border。
2. 主工作区头部默认不需要下边框。
3. Dock 头部必须有下边框。
4. 列表行激活态不加边框。
5. 菜单边框使用主题 token。

### 8.3 圆角

规范：

1. 工作区圆角：`18-22px`。
2. Activity button：`10-14px`。
3. 列表行：`8-12px`。
4. 菜单：`12-16px`。
5. 卡片只用于重复项、浮层、编辑器容器，不要到处套卡。

### 8.4 字体

规范：

1. 工作台内标题多用 `13-15px`。
2. 面板列表主文字默认 `13-14px`。
3. 次级说明 `11-12px`。
4. 项目名、客户名、文件夹名不默认加粗。
5. 对话名、工单名可中等字重，但不要重到像页面标题。
6. 不使用负 letter-spacing。
7. 不用 viewport width 缩放字体。

## 9. 复现检查清单

在新业务中使用这份规范时，至少完成以下检查。

布局：

1. 是否存在稳定的 `ActivityRail + ActivityPanel + WorkspaceFrame + OptionalDock` 骨架。
2. ActivityRail 与 ActivityPanel 是否视觉一体。
3. 工作区是否被外层区域包裹，而不是漂浮在整页白底或黑底上。
4. Dock 是否内嵌在 WorkspaceFrame 内，而不是默认弹窗。

主题：

1. 深色主题是否有层级，而不是纯黑一片。
2. 浅色主题是否解决外层白边问题。
3. 颜色是否全部通过语义 token 管理。
4. hover、selected、border、menu 是否使用统一 token。

组件：

1. 按钮、icon、菜单、列表行是否统一。
2. “更多”菜单是否不会被遮挡。
3. 列表行 hover 是否不改变尺寸。
4. 新建、折叠、更多、关闭等通用动作是否使用一致 icon。

交互：

1. 重命名、删除、归档、置顶等操作是否优先内联。
2. 可折叠组件是否都有动画。
3. loading、成功、失败、disabled 是否有明确反馈。
4. 切换 Activity 时，用户是否仍能理解当前工作上下文。

响应式：

1. 桌面端是否能并排显示 Context List、Workspace、Dock。
2. 平板端 Dock 是否改为覆盖式，而不是挤压主工作区。
3. 移动端是否拆分列表和工作区，而不是缩小桌面布局。
4. 输入区是否在各尺寸下都可用。

## 10. 一句话标准

这个风格的判断标准是：用户打开产品后，应该感觉自己进入了一个可靠的专业工作台，而不是进入一组临时拼装的页面；迁移到任何业务时，都应先保持工作台骨架、信息密度、内联交互和深浅色主题一致，再替换业务对象与品牌表达。
